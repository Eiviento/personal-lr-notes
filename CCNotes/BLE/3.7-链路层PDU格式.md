# 3.7 链路层 PDU 格式

## 一、PDU 总分类

```
链路层 PDU（连接状态）
├── LL Data PDU     ← 承载上层数据 (L2CAP→ATT→GATT)
└── LL Control PDU  ← 链路层自身管理
```

## 二、LL Data PDU 结构

```
Header(2) + Payload(0~251B) + MIC(4B, 加密时) + CRC(3B)
```

**Header 字段**：

| 字段 | 大小 | 含义 |
|------|------|------|
| LLID | 2 bit | 01=数据空包/继续片段, 10=数据起始片段, 11=控制PDU |
| NESN | 1 bit | Next Expected SN（确认+期望对方下一个包的序列号） |
| SN | 1 bit | Sequence Number（本包序列号, 0/1翻转，相同=重传） |
| MD | 1 bit | More Data（1=连接事件内还有更多数据） |
| RFU | 2 bit | Reserved |
| Length | 8 bit | Payload 长度，最大 251（BLE 4.2+, 之前27） |

**NESN+SN 确认重传机制**：SN 0/1 翻转，连续两包 SN 相同说明是重传；NESN 告诉对方"你上一包我收到了，期待你的下一个 SN"。

## 三、LL Control PDU 结构

```
Header(LLID=11) + Opcode(1B) + Control Data(可变)
```

| PDU | Opcode | 方向 | 作用 |
|-----|--------|------|------|
| LL_CONNECTION_UPDATE_REQ | 0x00 | M→S | 更新连接参数 |
| LL_CHANNEL_MAP_REQ | 0x01 | M→S | 更新信道图 |
| LL_TERMINATE_IND | 0x02 | 双向 | 断开连接 |
| LL_ENC_REQ/RSP | 0x03/04 | M↔S | 加密请求/响应 |
| LL_START_ENC_REQ/RSP | 0x05/06 | M↔S | 开始加密 |
| LL_FEATURE_REQ/RSP | 0x08/09 | 双向 | 特性交换 |
| LL_VERSION_IND | 0x0C | 双向 | 蓝牙版本号 |
| LL_REJECT_IND | 0x0D | 双向 | 拒绝不支持的 Control |
| LL_PHY_REQ/RSP | 0x14/15 | 双向 | PHY 切换 (5.0) |

## 四、加密范围

- **Header**：始终明文（方便链路层快速解析）
- **Payload + MIC**：加密（保护 GATT 数据 + 防篡改）
- **CRC**：始终明文（物理层误码检测，和加密无关）

## 五、数据包逐层封装实例

```
App: readCharacteristic() → ATT_READ_REQ(3B)
  → L2CAP 加 Header: [Length][CID=0x0004][ATT_READ_REQ] (7B)
  → Link Layer: [Header(LLID=10,SN,NESN,MD)][L2CAP包][CRC]
  → PHY: GFSK 调制 → 2.4GHz 发出
```

## 六、阶段三知识地图

广播阶段：状态机→广播信道→广播PDU(4种)→广播参数
         ↓ SCAN_REQ/RSP + CONNECT_IND
连接阶段：状态机(Connection)→数据信道跳频→LL Data/Control PDU→连接参数(Interval/Latency/Timeout/Channel Map)

## 问答记录

### Q1：LL Data PDU 和 LL Control PDU 是什么关系？

**核心比喻**：

```
LL Data PDU    → 运货的卡车（ATT/GATT 业务数据）
LL Control PDU → 修路的工程车（管理连接本身）
```

它们共用同一个物理信道、同一种包格式、同一套 SN/NESN 确认机制，**区别仅在于 Header 里的 LLID 字段**：

| LLID | 类型 | 含义 |
|------|------|------|
| 10 | LL Data PDU | 数据起始片段，Payload 传给 L2CAP |
| 01 | LL Data PDU | 空包（维持心跳）或分片续传 |
| 11 | LL Control PDU | 控制命令，链路层自己处理 |

---

**同一条连接事件里，Control 和 Data 可以交替发**：

```
连接事件（每 30ms 一次）

  ┌─── Master ──────────────────────────────────→ Slave ───┐
  │                                                         │
  │ ① LL Control PDU (LLID=11):                            │
  │    [Header|Opcode=0x03|ControlData]                      │
  │    LL_ENC_REQ → "先加密这条链路"                          │
  │    ← Opcode 在 LL 层，明文                                │
  │                              ← LL_ENC_RSP                │
  │                                                         │
  │ ② LL Control PDU (LLID=11):                            │
  │    [Header|Opcode=0x05|ControlData]                      │
  │    LL_START_ENC_REQ → "开始用新密钥"                      │
  │    ← Opcode 在 LL 层，明文                                │
  │                              ← LL_START_ENC_RSP          │
  │                                                         │
  │ ③ LL Data PDU (LLID=10):                               │
  │    [Header|──── Payload(加密) ────|MIC|CRC]              │
  │    ← LL 层没有 Opcode 字段！                              │
  │    解密后 Payload 里 → L2CAP → ATT [Opcode=0x12]         │
  │                              ← LL Data PDU(空包)          │
  └─────────────────────────────────────────────────────────┘
```

**比较**：

| | LL Data PDU | LL Control PDU |
|---|---|---|
| **识别** | LLID = 10 或 01 | LLID = 11 |
| **谁处理** | 扔给 L2CAP → ATT → App | 链路层自己处理，不上传 |
| **内容** | GATT 读写/通知数据 | 加密协商、参数更新、断开 |
| **有 Opcode 吗** | LL 层没有；ATT 层的 Opcode 在加密 Payload 里 | LL 层有 1 字节 Opcode，始终明文 |
| **对 App 可见** | ✅ onCharacteristicRead/Write/Changed | ❌ App 看不到 Control PDU |

### Q2：开始加密后的 LL Data PDU 中就没有 Opcode 了吗？

**LL Control PDU 有 LL 层的 Opcode（始终明文），LL Data PDU 没有 LL 层 Opcode，但它肚子里装的 ATT 包有 ATT 层的 Opcode（加密后从空中不可见，解密后完好无损）。**

这是两个层级的两套 Opcode：

| | LL Control PDU Opcode | ATT PDU Opcode |
|---|---|---|
| **所在层** | 链路层 | ATT 层（在 Data PDU 加密 Payload 里） |
| **位置** | LL Header 后的第 1 字节 | L2CAP Payload 的第 1 字节 |
| **例子** | 0x03=LL_ENC_REQ, 0x02=LL_TERMINATE_IND | 0x0A=ATT_READ_REQ, 0x12=ATT_WRITE_REQ |
| **加密影响** | 永远不加密，始终明文 | 加密后随 Payload 一起变成密文 |

**加密不影响协议结构本身**——ATT Opcode 一直在那儿，解密后还是原来的值。

---

**LL Data PDU 完整结构示例（发送 ATT Write Request to CCCD）**：

```
┌──────────────┬────────────────────────────────────────────┬───────┬─────┐
│  LL Header   │              Payload (加密)                 │  MIC  │ CRC │
│  LLID=10     │ ┌──────────┬───────────┬─────────────────┐ │       │     │
│  SN=0,NESN=0 │ │L2CAP头   │ ATT Opcode│  ATT Data       │ │       │     │
│  MD=0,Len=7  │ │Len=3     │  0x12     │ (Handle+CCCD值) │ │       │     │
│  (明文)       │ │CID=0x0004│(WRITE_REQ)│                 │ │(密文) │(明文)│
└──────────────┴─┴──────────┴───────────┴─────────────────┴─┴───────┴─────┘
                  └──────────────── 全部被 AES-CCM 加密 ────────────┘
```

**Header 永远明文**（链路层需要快速解析 SN/NESN/Length 做确认和重传），**Payload + MIC 被 AES-CCM 加密**，**CRC 永远明文**（物理层误码校验，和加密无关）。

### Q3：MIC 是什么？

**MIC = Message Integrity Check（消息完整性校验）**——加密包的"防伪印章"，4 字节，用于验证数据**没有被篡改**且**确实来自配对设备**。

**生成方式**：AES-CBC-MAC(SessionKey, Payload) → 4 字节 MIC，然后 MIC 随 Payload 一起被加密。

**校验方式**：接收方解密后重新计算 Payload 的 MIC，与收到的 MIC 比对——一致则通过，不一致则丢弃。

**MIC vs CRC**：

| | MIC | CRC |
|---|---|---|
| **目的** | 防**人为篡改** | 防**物理误码**（噪声） |
| **生成方式** | AES-CMAC（用 Session Key） | 多项式除法（公开算法） |
| **谁能验证** | 只有持有 LTK 的配对双方 | 任何人都能算 |
| **明文/密文** | 密文（随 Payload 加密） | 始终明文 |
| **被破坏后果** | 包丢弃，连接可能断开 | 包丢弃，等待重传 |

> CRC 防天灾，MIC 防人祸。

对于流量计场景：如果攻击者在中途把流速值从 0x01 改成 0xFF——有 MIC 则帧被丢弃等下一帧正确数据，无 MIC 则 App 显示错误读数。

### Q4：底层都是广播，蓝牙协议交互就是在不停地广播对吗？

**对了一半。** 物理层确实如此——所有 BLE 通信都是 2.4GHz 电磁波辐射，无方向性。但链路层通过三种机制在广播的物理介质上构建了排他的逻辑信道：

```
                    PHY 层              Link Layer
                   ────────           ────────────
广告阶段：    电磁波广播 ←──────→  真广播：谁都能解析
                              (固定 37/38/39 信道，固定格式)

连接阶段：    电磁波广播 ←──────→  假广播：只有配对设备能解析
                              (跳频+时间同步+Access Address 过滤)
```

**三种排他机制**：

1. **Access Address（32 位随机数）**：连接建立时 CONNECT_IND 下发，附近设备即使碰巧在同一信道，Access Address 不匹配，链路层直接丢弃
2. **自适应跳频**：37 个数据信道之间跳跃，外人不知道下一跳去哪个信道
3. **精确时间同步**：双方只在约定时刻（连接事件）醒来几百 μs，其余时间深度睡眠

> 像两个人约好：周三下午 3 点 17 分，在 3 号楼的第 18 个房间见面。别人既不知道时间、不知道地点，到了门口也没暗号（Access Address）。

这也是 **BLE 低功耗的关键**——不是"一直广播"，而是"精准约会、约完就睡"：

```
连接事件（30ms 间隔）：

  30ms ──────────────────────────────── 30ms ──────────────────
  ┌────┐                              ┌────┐
  │发包│  ← 只在这 300μs 醒着            │发包│
  └────┘                              └────┘
        └──────── 29.7ms 深度睡眠 ────────┘
```

> 无线电层面确实都是广播（电磁波无方向性），但链路层通过 Access Address + 自适应跳频 + 精确时间同步三种机制，在广播的物理介质上构建了一个排他的逻辑信道。**连接不是"不停广播"，而是"不停约会"。**

### Q5：为什么 LL Data PDU 中不包含 HCI ACL 包头？

**HCI 头不过空中那道线。** HCI 是 Host 和 Controller 两片芯片之间的内部通信协议，不是空中协议的一部分。

```
你的手机：

  ┌──── Host（主 CPU）────┐          ┌── Controller（蓝牙 IC）──┐
  │ App → ATT → GATT      │  HCI ACL │ 链路层 → PHY            │
  │          ↓            │ ──────→  │   ↓                     │
  │        L2CAP          │  UART    │  组装 LL Data PDU       │
  │     [包好 ATT 数据]    │          │  [拆掉 HCI 头]           │
  └───────────────────────┘          └─────────────────────────┘
```

**HCI 像快递面单**——Host 发给 Controller 时用来标注"这是发给哪条连接的"，Controller 收到后撕掉面单，只把 L2CAP 包装到 LL Data PDU 里。

完整的数据封装-解封链路：

```
发送端：ATT → L2CAP → +HCI头(发往Controller) → =Controller拆HCI头= → LL Data → PHY → 空中
接收端：空中 → PHY → LL Data → +HCI头(发往Host) → =Host拆HCI头= → L2CAP → ATT → App

HCI 头只在芯片间 UART 上传，永远不进入 2.4GHz 频段
```

### Q6：LL Data PDU 的报文格式中没看到地址，怎么知道发给谁？

**LL Data PDU 确实没有 MAC 地址字段。地址已经被"折叠"进连接参数了。**

CONNECT_IND（广播阶段唯一一次传地址）之后，双方用 **Access Address（32 位随机数）替代 MAC 地址**：

```
Advertising PDU (广播)：              LL Data PDU (连接)：
┌──────────────────┐                 ┌──────────────────┐
│ Header │ AdvA(6B)│                 │ Header │ Payload │
│        │  MAC地址 │                 │ 没有地址字段!     │
└──────────────────┘                 └──────────────────┘
                                            ↑
                                   CONNECT_IND 里下发的
                                   32 位随机数替代了地址
```

连接建立后，设备收到一个包的判断逻辑：

```
① 信道对吗？      → 我此刻就在这个时间，这个信道上听
② 时间对吗？      → 连接事件的精确时刻
③ Access Address 对吗？ → 包最前面 4 字节匹配吗？

匹配 → 这就是发给我的！收 Payload
不匹配 → 链路层硬件直接丢弃，不消耗 CPU
```

**多连接区分**：Central 可以连多个设备，每个连接有唯一的 Access Address，通过它区分哪个包来自哪个设备。

### Q7：LL Data PDU 前面是不是还得加 Access Address？真实抓包是什么样的？

**对。Access Address 是 PDU 外面的帧头，不是 PDU 的字段。**

```
BLE 空中完整帧结构（真实抓包）：

┌────────┬──────────────┬──────────────────────────────────┬───────┬─────┐
│Preamble│Access Address│            PDU                    │  MIC  │ CRC │
│ 1 字节  │   4 字节      │ ┌──────────┬──────────────────┐ │ 4 字节 │3 字节│
│ 0xAA   │  (32-bit)    │ │ LL Header│    Payload        │ │       │     │
│        │               │ │  2 字节   │  0~251 字节       │ │       │     │
└────────┴──────────────┴─┴──────────┴──────────────────┴─┴───────┴─────┘
                            └──────────── 我之前的图只画了这部分 ────┘
```

**广告包 vs 数据包的 Access Address**：

```
广告包：Access Address = 0x8E89BED6  ← 固定值，蓝牙规范定死的
数据包：Access Address = 0x????????  ← CONNECT_IND 里下发的随机值
```

**Wireshark 抓包对应**：

```
Frame 42: 47 bytes on wire
    [Preamble: 0xAA]
    Access Address: 0x9B3C7152        ← 4 字节，匹配才收
    [PDU Header]
        LLID: 10 (Data PDU)
        NESN: 1, SN: 0, MD: 0
        Length: 7
    [L2CAP Payload]                   ← 7 字节
        Length: 3
        CID: 0x0004 (ATT)
        [ATT]
            Opcode: 0x12 (Write Request)
            Handle: 0x0012
            Value: 01 00              ← CCCD=0x0001
    CRC: 0x1A2B3C
    [MIC: present, encrypted]
```

> **Access Address 不是 PDU 的字段，它是 PDU 外面的帧头。链路层硬件收到信号后先比对 Access Address——匹配了才收 PDU，不匹配直接扔。所以你确实不会在 PDU 结构里看到地址——它不在 PDU 里，它在 PDU 前面。**

### Q8：LL Data PDU 是广播包吗？"广播"到底怎么理解？

**物理学的"广播" ≠ 协议的"广播包"**：

| | 物理"广播" | 协议"广播包"（Advertising PDU） |
|---|---|---|
| **含义** | 电磁波无方向性辐射 | LLID=00/01，37/38/39 信道，固定格式 |
| **范围** | 所有 BLE 包的物理传输方式 | 特指广告阶段的包 |
| **LL Data PDU** | ✅ 物理上是电磁波广播 | ❌ 协议上不是广播包 |

```
Advertising PDU：
  物理上是广播 + 协议上也是广播 = 真广播，谁都能解析

LL Data PDU：
  物理上是广播 + Access Address 过滤 = 物理广播介质上的逻辑单播
  范围内的设备电磁波确实都能"听到"，但 Access Address 不匹配的
  在链路层硬件就丢掉了，根本不上传
```

### Q9：加密的 LL_ENC_REQ 是 Control PDU，它属于 Data PDU 的一部分吗？

**不。Control PDU 和 Data PDU 是平级的，不存在谁属于谁。**

```
LLID=11 (Control PDU)                LLID=10 (Data PDU)
───────────────────                  ──────────────────
LL_ENC_REQ         ← 加密协商        ATT Write Request   ← 业务数据
LL_START_ENC_REQ   ← 加密启动        ATT Notification    ← 业务通知
LL_TERMINATE_IND   ← 断开连接        空包                 ← 心跳确认

Control = 工程车（修路）   Data = 卡车（运货）
工程车不运货，卡车不修路。
```

同一条连接事件里，Control 和 Data 可以交替发——先用 Control 建立加密通道，再用 Data 传加密后的业务数据。

### Q10：前导码（Preamble）能理解成"收发双方约定数据开始的地方"吗？它和串口的开始位一样吗？

**方向对了一半：都跟"同步"有关，但分工不同。**

```
串口开始位  → 起跑枪："砰！"（标记起点 + 对齐采样时钟，一个位同时干两件事）
BLE 前导码  → 发令前的"各就各位——预备"（训练序列，给接收机热身）
BLE 接入地址 → 真正的起跑枪："砰！"（标记"这是我的包，数据从这里开始"）
```

**串口开始位干了什么（对比基准）**：

- 空闲时线保持高电平，开始位拉低 1 个位时 → 接收方看到**下降沿**，知道"来了！"
- 两个作用一次完成：① 标记一字节的开始；② 提供同步沿——双方波特率提前配好，接收方从下降沿往后推，在每位正中间采样
- 为什么 1 个位就够：**有线 + 波特率预先约定 + 线一直通着**，一个边沿足以对齐采样时钟

**BLE 前导码干了什么**：

- 1 字节（8 bit），内容是 `01010101`(0x55) 或 `10101010`(0xAA) 的交替比特串；交替方向由接入地址第一个比特决定
- 三个作用，全是给接收机射频硬件"热身"：
  1. **AGC（自动增益控制）**：无线信号忽强忽弱（远时只有 -90 dBm），放大器增益要先自动调到合适大小
  2. **锁频（频偏校正）**：双方晶振都有误差（ppm 级），2.4 GHz 上会差几十 kHz，接收机要先估计并校正
  3. **恢复符号时钟**：确定每个比特的边界在哪
- **它本身不是"起点标记"**——空中的 0101 噪音到处都是，接收机不会因为看到交替比特就认为"包开始了"

**真正"约定好数据开始的地方"是 Access Address**：

- 32 bit，接收机把收到的比特流和约定的值**逐个比对（相关检测）**，匹配上 → 才认定"有个包开始了"
- 广告包固定 `0x8E89BED6`，数据包是建连时 CONNECT_IND 下发的随机值
- 前导码的意义就在于：**让接收机在 AA 到来之前把状态调好**，AA 一到就能准确识别、不漏不错

**为什么 BLE 不能像串口那样用一个位搞定**：

| 差异 | 串口 | BLE |
|------|------|-----|
| 传输介质 | 有线，信号稳定 | 无线，信号弱且忽大忽小 → 需要 AGC |
| 频率/时钟 | 波特率提前配好 | 晶振有频偏 → 需要锁频 |
| 数据形态 | 连续字节流，一次同步一劳永逸 | 突发式（每个连接事件只发一两包），**每包都要重新同步** |

所以串口只要一个边沿，BLE 要一个字节的交替序列当"训练场"。

**一句话总结**：前导码 ≈ 串口开始位的"同步"作用 + 额外热身功能；而"约定好数据开始的地方"这个角色，在 BLE 里是**接入地址**承担的。

### Q11：MIC 可以理解成"消息签名"一样的机制吗？

**精神上很像，严格说是签名的"对称版兄弟"——MAC（消息认证码），不是数字签名。**

**像的地方（你的直觉对的部分）**：

- 都是一小段贴在消息后面的"密文标签"
- 验证者一验就知道：消息有没有被改、是不是持钥者发的
- 和签名一样：防篡改、认证发送方

**不像的地方（本质区别）**：

```
数字签名：私钥签、公钥验 → 私钥只有你自己有
BLE MIC ：同一把共享密钥签和验 → 双方都有 LTK/SessionKey
```

由此产生一个能力差异——**不可抵赖性**：

- 签名：全世界都能拿你的公钥验证"这确实是你私钥签的"，你赖不掉
- MIC：对方也握着同一把钥匙，你完全能自己造出一个"看起来是对方发的"MIC。在两人世界里，收到有效 MIC 说明"对方持钥"（所以 B 知道是 A 发的）；但拿去给第三方看，无法证明"这是 A 发的而不是 B 自己造的"

**类比**：

| | 相当于 |
|---|---|
| 数字签名 | 你的**手写签名/私人印章**：独一无二，公开可对笔迹验证，赖不掉 |
| BLE MIC | 两人的**接头暗号**：对上就是自己人，但你自己也能装对方说暗号，外人分不清 |

（Q3 里说 MIC 是"防伪印章"——那是签名的类比；更精确的类比其实是"共享暗号"。）

**对比总表**：

| | 数字签名 | BLE MIC |
|---|---|---|
| 家族 | 数字签名（非对称） | MAC（对称密钥） |
| 密钥 | 私钥签 / 公钥验 | 双方共享同一把 SessionKey |
| 防篡改 | ✅ | ✅ |
| 认证发送方（两人之间） | ✅ | ✅ |
| 不可抵赖（向第三方证明） | ✅ | ❌ 对方也能造 |
| 计算成本 | 高（大数运算，毫秒级） | 低（AES 硬件加速，微秒级） |

**为什么 BLE 不用真签名而是 MIC**：每个包都要带校验标签，签名运算贵、标签长，低功耗设备扛不住。配对时双方已通过 LE Secure Connections 用 ECDH 交换出共享密钥，之后每包用对称的 AES-CBC-MAC 生成 4 字节 MIC——又快又省电，足够满足"防篡改 + 确认对方"这两个需求。
