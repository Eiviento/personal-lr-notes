# 6.4 UUID 体系

## 一、什么是 UUID

128-bit 全球唯一标识符。BLE 用 UUID 标识 Service/Characteristic/Descriptor。

## 二、16-bit vs 128-bit UUID

蓝牙 SIG 预分配 16-bit UUID，放入固定的 128-bit Base UUID：

```
Base UUID: 0000XXXX-0000-1000-8000-00805F9B34FB
           ↑ 16-bit UUID 填入这里

例：0x180F → 0000180F-0000-1000-8000-00805F9B34FB
```

优点：协议包更小、广播数据省空间、全局不冲突。

## 三、U UID 分配规律

| 前缀 | 类别 | 示例 |
|------|------|------|
| 0x18XX | Service | 0x180F=Battery, 0x181A=Env Sensing |
| 0x2AXX | Characteristic | 0x2A19=Battery Level, 0x2A6E=Temperature |
| 0x29XX | Descriptor | 0x2902=CCCD, 0x2901=CUD |

## 四、仪器仪表相关标准 UUID

0x181A (Env Sensing) / 0x2B18 (Volume Flow Rate, 5.3) / 0x2A58 (Analog Input) / 0x2A5C (Digital Output)

## 五、厂商自定义 128-bit UUID

用 UUID v4 随机生成（uuidgen / [guid]::NewGuid()），不要手动编。
建议：公司统一 Base UUID，各 Service/Characteristic 从 Base UUID 派生。

## 六、混搭策略

- Device Info / Battery → 16-bit 标准（任何工具可解析）
- 流量计核心 Service + 特征 → 128-bit 自定义
- CCCD → 16-bit 标准（0x2902，规范强制）
- Android: `UUID.fromString("0000180f-0000-1000-8000-00805f9b34fb")`

## 问答记录

### Q1：什么时候用 16 位 UUID，什么时候用 128 位的？

**决策规则一句话：看这个 Service/Characteristic 是谁定义的——标准功能用 16 位（SIG 发的号），自定义功能用 128 位（自己随机生成的号）。**

**为什么这么分**：

- 16 位空间只有 2^16 ≈ 6.5 万个号，**必须由蓝牙 SIG 统一注册分配**才能保证不撞车。所以 16 位 UUID 只属于标准服务/特征（0x180F 电量、0x180D 心率、0x2902 CCCD……），你**不能自己随便编一个 16 位值来用**。
- 128 位空间约 3.4×10^38，用 UUID v4 随机生成，撞车概率≈0，**无需注册**——自定义/私有功能（如流量计的私有协议）直接用。

**类比**：

```
16 位 UUID  = 官方统一发的"公共号牌"（电话簿里的公共号码，人人都认识）
128 位 UUID = 你自己生成的身份证号（自己用，不对外注册，也没人跟你抢）
```

**对比表**：

| | 16 位 UUID | 128 位 UUID |
|---|---|---|
| 谁发的 | 蓝牙 SIG 官方注册分配 | 自己随机生成（UUID v4） |
| 用于 | 标准服务/特征/描述符 | 厂商私有/自定义服务 |
| 空间 | 2^16 ≈ 6.5 万个，SIG 统一管理 | 3.4×10^38，撞车概率≈0 |
| 占用字节 | ATT 里 UUID 字段 2 字节 | 16 字节 |
| 附带好处 | 通用 App/工具都认识，互操作性好 | 想怎么定怎么定 |

**功能上完全等价**——都是标识 Service/Characteristic 的号牌，差别只在"谁发的牌 + 占多少字节"。

**常见坑**：

- 把标准特征（如电量）硬改成自定义 128 位 → 合法，但通用 App 不认识，失去互操作性
- 自定义功能硬塞一个没注册的 16 位 → 可能和别家厂商撞号
- 转换只有一条路：16 位套 Base UUID 模板 `0000XXXX-0000-1000-8000-00805F9B34FB` 得到 128 位；**128 位不能随便截成 16 位**
