# 3.6 连接事件与自适应跳频

## 一、Connection Event：连接后的心跳

```
        Conn Interval (如 30ms)
  ├─────────────────────────────────────┤
  │         Connection Event            │    休眠...
  │  Master → Slave  (数据包)           │
  │         ← IFS 150μs →              │
  │  Slave → Master  (回复包)           │
  │         ← IFS 150μs →              │
  │  Master → Slave  (可再来多轮)        │
  └─────────────────────────────────────┘
```

规则：Master 先发包；Slave 必须 150μs 内回复；可多轮直到双方发空包；Slave 可借 Latency 跳过整个 Event。

## 二、150μs 回复窗口

BLE 极速反应的设计——快速关射频省电 + 避免信道长时间占用。Slave 不回则浪费这个 Event，下个 Interval 跳新信道。

## 三、自适应跳频（AFH）

### 跳频算法
`next_channel = (current + hopIncrement) % 37`，hopIncrement 须与 37 互质（5~16）。

### Channel Map 更新
37-bit 位图。某信道 CRC 连续失败 → Master 标记为坏 → 发 LL_CHANNEL_MAP_REQ 通知 Slave → 跳频时通过重映射算法自动绕过。

### 重映射规则
`remapping_index = hopIncrement % num_used_channels`，从可用信道列表重选。即使只剩 2 个可用信道仍能工作。

## 四、空包与 Slave Latency

**空包（Empty PDU）**：Header Length=0，表示"我还在但没数据"。

Latency 配合空包：Slave 每 Latency+1 个连接事件至少回复一次（带数据或空包），不能超过 Timeout/2，否则连接被误断。

## 五、连接参数动态更新

Slave 可发 LL_CONNECTION_PARAM_REQ 请求更新，Master 可发 LL_CONNECTION_UPDATE_REQ 单方面更新。Android 中 `requestConnectionPriority()` 就是发参数更新请求，但设备可拒绝。

## 六、Connection Event 结束条件

双方都发 MD=0（More Data=0）的包 → Master 决定关闭 → 或达到 CE Length 限制。

## 七、对开发的影响

- 150μs 回复由硬件控制，App 不可见
- 自适应跳频让连接很可靠，短暂干扰不会立刻断
- 参数更新只是"请求"，需用 `onConnectionUpdated()` 确认
- Wi-Fi 干扰导致连接变慢正常（可用信道减少），但通常不断

## 问答记录

### Q1：链路层是不是"一包发完等对方确认才能发下一包"？为什么应用层抓包看到主机连发好多包、设备最后才应答？

**是的，链路层严格"一包一确认"（停等式，stop-and-wait）——但那个"确认"是空包，发生在每一对包之间，你在应用层日志里看不见。两个现象不矛盾，它们发生在不同层。**

**三层应答概念**：

| 层 | 应答物 | 谁生成的 | 应用层看得见吗 |
|---|---|---|---|
| 链路层 | 空包（NESN 确认） | 硬件自动，150μs 内回 | ❌ 看不见 |
| ATT 层 | Write Response / Confirmation | 协议栈，看 PDU 类型 | ✅ |
| 应用层 | 业务应答（"全部收到"） | 你的代码 | ✅ |

**真相还原**：

```
空中实际发生（链路层视角）：
 M: Write#1 ──→    ←── 空包 ACK（应用层日志里没有）
 M: Write#2 ──→    ←── 空包 ACK
 M: Write#3 ──→    ←── 空包 ACK
 S: "全部收到"  ← 这是应用层业务应答

应用层日志只显示：Write×3 → 应答×1
```

**"连发多包才应答"的两个来源**：

1. **ATT 层本来就规定不答**：Write Command（无确认写）、Notification 都规定接收方不回 ATT 应答——但链路层仍在每个包后面默默空包确认。
2. **业务层设计**：设备 App 协议自己定义"收齐 N 个分包后回一个总应答"。

**同一连接事件内的"多轮"**：MD=1 表示"我还有数据"，可以在一个连接事件内多打几个来回，但每轮仍是一发一回应——确认机制始终在，只是打包在同一事件里，时间上更紧凑。

**没收到 ACK 怎么办**：发方在下一个连接事件重传同一包，应用层完全无感知。

**广播 vs 连接**：广播状态（Advertising）**没有确认机制**——发了不保证被收到，也不需要对方确认；"一包一确认"是连接建立后才有的机制。

### Q2：蓝牙是全双工吗？从机（外设）能主动发数据吗？

**不是全双工——BLE 是半双工（TDD 时分双工）：同一时刻只有一方能发。**

**类比**：

```
对讲机（半双工）：按下才说，松手才能听
打电话（全双工）：边说边听，互不干扰
BLE = 对讲机，只是"按下/松开"切换快到毫秒级
```

**时序规则**：每个连接事件 **Master 先发，Slave 必须在 150μs 内回应**。Slave 不能在其他任何时刻发射——从链路层看，Slave 的每一次发送都是"应答式"的。

**"设备能主动发吗"分两层看**：

| 层面 | 能否主动 | 说明 |
|---|---|---|
| 内容上 | ✅ 能主动 | Notify/Indicate 就是设备主动上报（电量、传感器数据、流量计数据），想发什么完全由设备决定 |
| 时机上 | ❌ 不能主动 | 必须等 Master 打开下一个连接事件并先发一个包（哪怕空包），Slave 才能带上数据回应 |

所以从机"有数据想发"到"真正发出"的最坏延迟 ≈ **一个连接间隔**（7.5ms~4s，常用 30~50ms）；开了 Slave Latency 更久（最多 latency+1 个间隔）。

**为什么这么设计**：半双工 + Master 定时轮询，从机才能只在事件里短暂醒来、其余时间深度睡眠——**这是 BLE 低功耗的根基**。如果从机能随时发射，就得一直醒着防碰撞，功耗爆炸。

**数据急着发怎么办**：

- 缩短连接间隔（connection interval）
- 回应包里设 **MD=1** 表示"我还有数据"，Master 会在同一事件里多开几轮，提高单事件吞吐

**顺带**：经典蓝牙（BR/EDR）同样是时分半双工——打电话"边听边说"其实是微秒级快速轮流，快到人感觉不到。
