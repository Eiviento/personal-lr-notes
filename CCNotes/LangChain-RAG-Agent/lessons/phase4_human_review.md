# Phase 4.3：人工审核环节 —— 草稿 → 机审 → 人确认 → 终稿

> 对应脚本：`scripts/phase4_3_human_review.py`
> Phase 4 收官：把 3.2 的 LLM 评审、4.2 的工具校验和"人"串成最后一道工序。

---

## 为什么需要人在回路（Human-in-the-loop）

LLM 产出不能直接发布——协议规范要交给同事用，错误代价高。机审（LLM 评审 + 工具校验）各有盲区，最后一关必须是人。

## 流程与两层机审分工

```
协议草稿 JSON
  │
  ▼ 机审两层（自动）
  ├─ 代码校验：死规则，精确 —— 类型/字节数不匹配必被揪出（4.2 的 FIXED_SIZE）
  └─ LLM 评审：开放问题，洞察 —— "清零阈值缺失""无异常状态"这类
  │
  ▼ 人工逐条处理：[1]自动修正（有确定性 fix）/ [2]忽略 / [3]记录待办
  │
  ▼ 终稿：<名称>_final.json + _final.md（附审核记录表）+ _review_log.json
```

实测中两层还展示了**互补**：人为注入的 `msg_type` 字节数错误，代码校验和 LLM 评审**各自独立**发现了它——代码靠规则，LLM 靠知识。

## 三个设计决策

1. **草稿与终稿分离**：`*_protocol.json` 是草稿，人确认后另存 `*_final.*`——草稿永远可回退，终稿有权威版本
2. **自动修正只给确定性 fix**：代码校验"uint8 应为 1 字节"→ 一键改回；LLM 的"建议增加故障状态"没有程序化 fix，只能人判断后记待办
3. **全程留痕**：每条问题的处理决定写入 `_review_log.json`，终稿 MD 附审核记录表，页脚"已通过人工审核"——发布责任可追溯

## 交互设计细节

- 逐条提问而非列表勾选：人一次只做一个决定，注意力不分散
- `stdin` 可管道喂入：批量/测试场景用 `printf '1\n2\n3\n' | python ...`
- EOF 容错（默认忽略）+ 回车即确认：脚本化调用不卡死
