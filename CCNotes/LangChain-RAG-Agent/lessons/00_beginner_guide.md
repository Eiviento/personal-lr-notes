# 从零看懂这个项目：协议自动生成工具全解（新手版）

> **给完全没接触过 LLM 开发的人。** 不预设任何前置知识，按"是什么 → 做什么 → 为什么"的顺序讲。
> 读完这篇，你就知道：这个项目干了什么、每段代码存在的理由、以及背后的原理。

## 一、一句话目标

**输入**：同事写的一份需求文档（比如"水表要每天上报用水量，支持远程开关阀门……"这种文字）。
**输出**：一份规范的结构化协议定义（有哪些字段、每个字段什么类型、占几个字节、有哪些约束规则），JSON 给程序用，Markdown 给同事看。

一句话：**让 AI 把"人话"翻译成"协议规范"。**

---

## 二、动手前必须懂的三个底层概念

### 2.1 LLM（大语言模型）是什么：一个"接话"机器

DeepSeek、ChatGPT 这类模型，本质就干一件事：**你给它一段文字，它预测"最合理的下文"，一个字一个字接出来。**

它没有思想、不会执行代码、不会上网、不会算账。它只会一件事：**生成文字**。它很擅长模仿见过的海量文本风格——比如你让它按 JSON 格式回话，它大概率能模仿出来，但不是 100%。

这个"不是 100%"是理解整个项目的钥匙：**我们做的所有事情，本质上都是在给一个爱自由发挥的接话机器上保险，让它稳定输出我们想要的格式。**

### 2.2 API 是什么：模型不在你电脑上，API 是"订单格式"

模型太大（几百 GB），跑在厂商服务器上。你的程序想用它，就发一条"订单"到服务器，服务器把回复发回来：

```
你的电脑 ──请求(你的文字 + 配置)──► DeepSeek 服务器
你的电脑 ◄──响应(AI 生成的文字)── DeepSeek 服务器
```

- **API**：这份订单的格式约定（请求里放什么、回复长什么样）
- **API Key**：一张门禁卡（一串密码），证明你有权使用；本项目从环境变量 `DEEPSEEK_API_KEY` 读取
- 本项目用 DeepSeek 的服务器，但它兼容 OpenAI 的订单格式，所以代码里出现 "OpenAI" 字样不用奇怪

### 2.3 为什么 AI 输出不稳定：它是概率机器

同样的问题问两次，答案可能不一样。它可能：
- 输出格式对，内容胡说（幻觉）
- 多输出一堆废话（"好的，以下是……"）
- JSON 少个逗号导致程序解析失败

所以项目里才需要 Prompt（把话说清楚）、Parser（容错解析）、校验（代码兜底）、人工审核（最后一道保险）——**每一层都是给概率机器上的保险。**

## 三、整体管线地图（先有全局，再进细节）

```
① 读文件            同事的需求文档 → 程序里的字符串
     ↓              （解决：中文乱码、文档太长）
② 需求分析          全文档 → 关键需求点列表         [AI 第 1 次调用]
     ↓              （解决：文档里废话太多，先提炼）
③ 字段定义          需求点 → 字段表 JSON            [AI 第 2 次调用]
     ↓              （可选：注入 RAG 检索到的历史协议模板）
④ 约束规则          字段表 → 取值范围/边界/异常      [AI 第 3 次调用]
     ↓              （解决：AI 生成时容易漏边界条件）
⑤ 合并              纯 Python 代码拼装最终协议        [不用 AI]
     ↓              （解决：机械活交给代码，100% 确定）
⑥ 校验（可选）       代码校验类型/字节数合法性        [模型"点菜"代码执行]
⑦ 人工审核（可选）   人逐条确认 → 终稿 + 审核记录      [最后一关是人]
⑧ 展示/下载          Web 页面（Streamlit）或 Markdown 文档
```

记住这张图。下面每一节 = 图上的一个节点，讲"做什么 + 为什么"。

## 四、每一步详解

### 4.1 读文件（scripts/phase3_1_doc_input.py 里的 read_doc）

**做什么**：把需求文档文件读成程序里的字符串。

**为什么要专门写**：两个现实问题——

| 问题 | 原理 | 解决办法 |
|------|------|---------|
| 中文乱码 | 中文文件有两种主流编码：UTF-8 和 GBK。同一串字节在不同编码下解读出不同的字，读错就满屏乱码 | 按 `utf-8-sig → utf-8 → gb18030` 顺序尝试解码，谁成功用谁（gb18030 兼容 GBK） |
| 文档太长 | 模型一次能"看"的文字有限（DeepSeek-chat 约 6.4 万 token，中文约 1 字符 = 1 token），太长直接报错 | 先估算长度，超限警告（根本解法是后面 4.6 的 RAG） |

**不做会怎样**：同事发来一个 GBK 编码的文档，程序直接崩溃；或文档太长，API 报错。

### 4.2 需求分析：为什么不让 AI 一步出最终协议？

**做什么**：第一次 AI 调用。输入整篇文档（含背景介绍、硬件清单、无关信息），输出提炼后的"关键需求点"列表。

**为什么不一步到位**——这是本项目最重要的设计思想之一：

| 一段式（一步出协议）的问题 | 拆成多步的解法 |
|--------------------------|---------------|
| 要求太多，AI 容易漏（比如"留扩展位"这种小要求） | 每步只干一件事，要求少就不容易漏 |
| 结果错了不知道哪一步错的 | 每步中间产物可见，哪步出错一眼定位 |
| 分析要"发散"（广撒网），字段定义要"严谨"，混在一个 Prompt 里只能取折中 | 每步可以单独调风格 |

**原理**：AI 是"接话"机器，你给的任务越长越复杂，它"接"偏的概率越大。**把大任务拆成小任务，是使用 AI 的第一原则。**

### 4.3 字段定义：Prompt 是什么

**做什么**：第二次 AI 调用。输入需求点，输出字段表 JSON（字段名/类型/字节数/范围……）。

**Prompt（提示词）是什么**：给模型的"任务说明书"。本项目每步都有一个"说明书"，包含四要素：

| 要素 | 本项目里的例子 | 作用 |
|------|--------------|------|
| 角色 | "你是一位资深的通信协议工程师" | 激活模型参数里协议领域的知识 |
| 指令 | "提取所有需要通信的数据字段" | 说清楚要干什么 |
| 上下文 | 需求点 + （可选）历史协议模板 | 给足材料，减少瞎编 |
| 输出格式 | 完整的 JSON 骨架示例 | 让模型照着填，而不是自由发挥 |

**为什么还要给"Few-shot 示例"（一个完整的输入→输出范例）**：描述十遍"字段名用英文驼峰"，不如一个例子直接——模型是模仿机器，**给例子比讲规则有效**。

**为什么要 JSON**：程序要吃结构化数据。JSON 是"程序能读的格式"，Markdown 是"人能读的格式"，两者分工（见 4.5）。

### 4.4 约束规则：让 AI"自己审自己"

**做什么**：第三次 AI 调用。输入字段表，输出约束规则 + 问题清单（评审视角）。

**为什么有效**：AI 生成字段表时是"设计者"视角，容易只顾着列字段；换成"评审专家"角色再读一遍，它会发现设计时没注意的问题。实测就抓到过真问题：*"用水量满量程自动清零后，怎么区分新旧数据？"*——这种问题，人工评审要逐条盯着文档才能想到。

**为什么评审用 AI 而不是纯代码**：代码只能查死规则（类型对不对、字节数对不对），查不了"预留扩展位 1 字节够不够装光照数据"这种**开放性问题**。两类检查互补。

### 4.5 Python 合并：为什么最后一步不用 AI

**做什么**：把前面几步的产出拼成最终协议 JSON。

**为什么用普通 Python 代码而不是第四次 AI 调用**——第二条核心设计思想：

> **AI 做"需要动脑"的事，代码做"机械"的事。**

合并是机械活：没有任何思考，就是把字段表和约束规则放进同一个 JSON。让 AI 干机械活有两个风险：① 多花一次钱和时间；② AI 可能在"合并"时手滑改写/丢掉字段。代码干机械活 100% 确定、免费、瞬间完成。

同样道理：**Markdown 文档的渲染也是纯 Python**（generate_protocol.py 里的 render_markdown）——协议长什么样不该有 AI 的随机性。

### 4.6 附加能力 A：RAG——让新协议风格和公司历史一致

**背景问题**：公司有历史协议模板（比如"水表协议字段叫 meter_id、total_flow"）。新协议最好沿用这个风格，但模板会越来越多，全塞进 Prompt 又长又贵又乱。

**做什么**（scripts/phase4_1_rag.py）：
1. 把每份历史模板变成一串数字——**向量**（embedding）
2. 新需求也变成向量，在库里找**距离最近**的几份模板
3. 检索到的模板拼进字段定义的 Prompt 当参考

**核心原理——为什么用向量而不是关键词搜索**："设备位置上报"和"GPS 经纬度"没有任何共同关键词，但意思相关。**向量是"意思"的数学表示：意思越接近，向量距离越近。** 关键词搜不到的东西，向量能搜到。

**一个向量是怎么算出来的**（embedding 内部就三步）：
1. 分词：把句子切成词（中文逐字切）
2. 推理：神经网络把每个词算成一个向量
3. 池化：整句的向量 = 各词向量合成一个（本项目用 [CLS] 特殊标记的向量）+ 归一化

**实测效果**：没 RAG 时字段叫 device_id/cumulative_volume（每次生成都漂移）；有 RAG 后叫 meter_id/total_flow——与公司水表模板逐字一致。

**注意**：本项目用的 BGE-small-zh 是**中文语义模型**。之前试过英文模型 MiniLM，对中文检索排序错乱（查"水表阀门"命中"环境监测"）——**嵌入模型必须匹配语言**，这是踩过的真坑。

### 4.7 附加能力 B：工具调用——模型"点菜"，代码"上菜"

**背景问题**："uint8 占 1 字节"是死规则。让模型背，它会背错；让代码算，永不出错。但"要不要校验""结果怎么解读"又需要模型的判断力。

**做什么**（scripts/phase4_2_tool_calling.py）：把函数的"说明书"（名字 + 参数格式）告诉模型。模型想要精确答案时，输出一个结构化的"调用请求"（函数名 + 参数），**你的代码真正执行函数**，结果回传，模型继续推理汇总。

```
模型："我要调用 validate_field_type(field_name='msg_type', length=2)"
代码：执行 → "uint8 应为 1 字节，声明 2 → 不合法"
模型："好的，汇总如下：msg_type 有问题，建议改成 1 字节……"
```

**安全本质**：模型只能"请求"调用，执行权永远在代码手里——AI 永远碰不到你的系统。

### 4.8 附加能力 C：人工审核——最后一关必须是人

**为什么**：AI 会自信地犯错，而协议规范发布出去同事要用，错了要担责。机器检查（代码校验 + AI 评审）各有盲区，最后拍板的必须是人。

**做什么**（scripts/phase4_3_human_review.py）：机审两层 → 问题清单 → 人逐条决定（自动修正/忽略/记录待办）→ 终稿单独保存 + 审核记录留痕。

**三个设计点**：
- 草稿和终稿分开存：确认前的草稿永远可回退
- 只有"确定性修正"才给一键按钮（uint8 改回 1 字节）；开放性问题只能人判断
- 每条决定的处理记录写进文件：将来查"这个字段当时为什么忽略"有据可依

### 4.9 附加能力 D：Web 界面（app.py）——让同事不用命令行

**做什么**：Streamlit 写的网页：上传文档 → 点按钮 → 看结果 → 下载。

**必须理解的一个机制**：Streamlit 和普通网页不同，**用户每次交互（点按钮、勾选、上传），整个 Python 脚本从头到尾重跑一遍**。这带来两个必学对策：

| 对策 | 解决的问题 |
|------|-----------|
| `st.session_state` | 重跑后变量清零。AI 调用一次要十几秒几毛钱，**结果必须存住**，不能用户切个标签就重新生成 |
| `st.cache_resource` | 模型客户端、向量库这些"昂贵资源"重跑时复用，不重复加载（本地模型加载要 1-2 秒） |

**架构原则**：UI 是薄壳。全部逻辑复用 scripts/ 里的零件，网页只干"上传、触发、展示、下载"四件事。

### 4.10 附加能力 E：错误处理（scripts/phase5_2_robust.py）

AI 服务会失败：超时（网络慢）、限流（429，请求太密被拒）、服务器抖动（5xx）。这些**重试有效**；而认证错误（4xx）重试一万次也没用，要**快速失败**并报错。

对策：`llm.with_retry(...)` 一行给模型调用加自动重试，配合**指数退避**（重试间隔 1s/2s/4s 递增 + 随机抖动，避免所有请求同一秒再涌上去）。同时用日志文件记录每次生成的成败和耗时，出问题可追溯。

## 五、灵魂拷问：为什么搞这么复杂，直接调 API 不就完了？

确实，最简版本 30 行代码就能"需求 → 协议"。这个项目每一步的复杂度，都是在回答一个问题：**"万一 AI 没按你说的做，怎么办？"**

| 环节 | 应对的风险 |
|------|-----------|
| Prompt 四要素 | 模型输出跑偏格式 |
| Few-shot | 模型不按你的风格写 |
| 拆成多步链 | 任务太长模型漏要求 |
| Parser 容错 | JSON 解析失败程序崩溃 |
| RAG | 新协议风格和公司历史不一致 |
| 工具校验 | 死规则被模型背错 |
| LLM 评审 | 设计者视角漏掉的边界问题 |
| 人工审核 | 以上全部失败时的最后兜底 |
| 重试 + 日志 | 服务抖动导致任务中断 |

每一层单看都是"过度设计"，但**对"概率机器"来说，每一层都在真实场景里失守过**——这个项目里都有实测证据。

## 八、概念速查表

| 术语 | 一句话解释 |
|------|-----------|
| LLM | 大语言模型，只会"接话"的文字生成机器 |
| API / API Key | 调远程模型的"订单格式" / 门禁卡 |
| Prompt | 给模型的任务说明书（角色+指令+上下文+输出格式） |
| Token | 模型计数单位，中文约 1 字 1 token |
| Few-shot | 在说明书里给"输入→输出"范例，让模型模仿 |
| 幻觉 | 模型一本正经地胡说 |
| LangChain | Python 库：把"调模型"包装成标准积木，便于组装 |
| LCEL / Runnable | LangChain 的管道写法（用 \| 串联）/ 统一的"输入→输出"积木接口 |
| Parser | 把模型输出解析成程序能用的类型（字符串/dict） |
| Embedding | 把文字变成"意思的坐标"（一串数字），意思近→距离近 |
| 向量数据库 | 存"坐标+原文"的仓库，支持按意思检索（本项目用 Chroma） |
| RAG | 检索相关内容塞进 Prompt，让生成更"懂行" |
| Tool Calling | 模型输出"函数调用请求"，代码执行后回传结果 |
| HITL（人在回路） | 关键环节插入人工确认 |
| Streamlit | Python 写网页的工具（不用 HTML/JS） |
| 指数退避 | 重试间隔逐次翻倍 + 随机抖动，防止惊群 |
