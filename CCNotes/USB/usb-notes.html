1.1 USB 设计目标与历史

USB 之前的七种接口和七种痛

接口痛点
RS-232 串口速度慢(115.2kbps)、不能热插拔、一端口一设备、需手动设参数
并口(LPT)电缆粗贵、速度~150KB/s、只能接打印机
PS/2不能热插拔、键盘鼠标不通用
SCSI贵、需专用卡、终端电阻/ID需跳线
Game Port只能一个游戏杆、CPU占用极高
VGA只传视频不传数据/供电
各类专用每加设备可能要加卡，IRQ/DMA/IO冲突

USB 七大设计目标

#目标对应设计决策
1一根线接所有外设统一物理层+协议层
2热插拔Host主动检测总线电平变化+枚举协议
3自动配置描述符→自动识别→不需要手动设地址
4支持多种速度1.5M/12M/480M/5G+ 分级
5总线供电VBUS 5V，低功耗设备不额外供电
6可扩展Hub级联，最多127设备
7低成本低速简单设备+分层协议

核心设计哲学

Host 中心化：所有通信由 Host 发起，Device 只能被动应答。

跟 MQTT 的根本差异：MQTT Client 可以随时 PUBLISH，USB Device 连打招呼的权利都没有。

名字含义

  • Universal — 通用
  • Serial — 串行
  • Bus — 总线

1.3 总线拓扑结构

树形拓扑规则

规则数值
最多层数7层(Tier)，Root Hub = Tier 1
最多设备127个（ADDR字段7bit，0x00保留）
最多非Root Hub5个
每段电缆最长5米(FS/LS)，总长30米

地址范围

ADDR字段 7 bit → 0x00~0x7F (128个)
    0x00 = 默认地址（Default Address），设备刚复位后使用
    剩余 1~127 = 127个可分配地址 → 127设备上限

三种角色

  • Host: 发起所有通信、提供VBUS(5V)、枚举、带宽调度、内置Root Hub
  • Hub: 扩展端口、检测插拔、端口供电、HS↔FS/LS速度翻译(Split Transaction)、本身也是USB Device
  • Device (Function): 响应请求、提供描述符、实现功能逻辑、管理电源

Compound vs Composite

  • Compound Device: 一个壳子多个地址（内含Hub+多个独立Device）
  • Composite Device: 一个地址多个Interface（一个芯片多功能，如摄像头+麦克风）

差分信号原理

D+和D-传差分信号：接收方计算 D+减D- 的差值。外部共模噪声同时影响两根线 → 相减后噪声抵消。

J/K 状态

状态D+D-LS含义FS含义
J (Diff 1)高低IdleData 1
K (Diff 0)低高Data 1Idle

速度识别（电阻决定）

Host/Hub侧: D+和D-各有15KΩ下拉到GND
    设备侧:
      FS/HS设备: D+ → 1.5KΩ上拉到3.3V → 插入后D+变高
      LS设备:    D- → 1.5KΩ上拉到3.3V → 插入后D-变高

HS Chirp 协商

HS设备先冒充FS(D+上拉) → Host复位 → 设备发Chirp K → Host回Chirp K/J交替 → 设备切换HS终端电阻 → 协商成功，后续以480Mbps通信。

NRZI 编码 + Bit Stuffing

  • NRZI: 0=跳变, 1=保持
  • Bit Stuffing: 连续6个1后强制插1个0(产生跳变维持时钟同步)

2.1 三层通信模型

三层定义

功能层 (Function Layer) — "做什么"
        → 你的SDK和业务逻辑
        → 例: HID按键→按键码, CDC→串口字节流, UVC→视频帧

    USB设备层 (USB Device Layer) — "怎么组织"
        → 端点/管道/传输类型/描述符
        → 把包的碎片组织成有意义的传输

    总线接口层 (Bus Interface Layer) — "怎么传"
        → 包(Packet)、NRZI编码、D+/D-信号
        → 硬件层面

MQTT 类比

MQTT层USB层
应用层 (Topic/Payload)功能层 (业务数据)
MQTT协议 (QoS/PacketID)USB设备层 (端点/管道/传输)
传输层 (TCP/IP)总线接口层 (包/D+/D-)

数据流转示例（读设备描述符）

功能层: "我要VID/PID"
        ↓
    设备层: 组装 GET_DESCRIPTOR(Device), bmReqType=0x80, bReq=0x06
        ↓
    总线接口层: SETUP Token + DATA0(8B) → IN Token×3 → DATA+ACK ×3
        ↓

2.2 端点 (Endpoint) 深入

定义

端点 = 设备内部的一段 FIFO 缓冲区。硬件概念，芯片设计时就要决定数量/大小/类型。

端点地址编码

Token包中 ENDP 字段 = 4 bits → 端点号 0~15

    完整端点地址:
      Bit7 = 方向 (1=IN, 0=OUT) — 在端点描述符中
      Bit3-0 = 端点号

      IN = Device → Host (Host "收进来")
      OUT = Host → Device (Host "发出去")

    方向永远从Host视角看！
    0x81 = IN, EP1    0x02 = OUT, EP2

端点0 (EP0)

属性值
端点号固定0
方向双向
传输类型只能是控制传输
职责枚举、配置、类特定控制请求
LS MaxPacketSize固定8B
FS MaxPacketSize8/16/32/64
HS MaxPacketSize固定64B

最大包大小 (MaxPacketSize)

速度控制中断批量等时
LS81~8❌❌
FS8/16/32/641~648/16/32/641~1023
HS641~10245121~1024

典型设备端点布局

HID键盘(LS): EP0(控制8B), EP1 IN(中断8B)
    CDC串口(FS): EP0(控制64B), EP1 IN(中断16B), EP2 IN(批量64B), EP3 OUT(批量64B)
    UVC摄像头(HS): EP0(控制64B), EP1 IN(中断16B可选), EP2 IN(等时512B)

2.3 管道 (Pipe) 深入

定义

管道 = Host软件到端点之间的逻辑通信通道。

两种管道

消息管道 (Message Pipe)流管道 (Stream Pipe)
方向双向单向
结构请求→响应格式原始字节流
连接端点只能连EP0连EP1~15
传输类型只能控制传输中断/批量/等时
MQTT类比CONNECT/CONNACKPUBLISH body

映射关系

消息管道 = 控制传输 = EP0 = 双向
    流管道 = 中断/批量/等时传输 = 非0端点 = 单向

补充：接口 (Interface) 与端点 (Endpoint) 的归属关系

关键理解：端点有主——每个端点只属于一个 Interface，但 EP0 是所有 Interface 共用的。
libusb 中 claim 接口获得端点使用权，传输时直接用端点地址。

核心规则四条

规则内容为什么
规则 1 每个非 EP0 端点只属于一个 Interface 端点地址在一个 Configuration 内必须唯一
规则 2 EP0 是共用资源，不属于任何 Interface 所有控制传输都走 EP0，bmRequestType 区分接收者
规则 3 同一 Interface 的不同 Alternate 可复用端点号 同时只有一个 Alternate 激活，不会冲突
规则 4 两个不同 Interface 不能声明同一端点号 USB 规范禁止——一个 Interface 用了 EP3，另一个不能再声明

真实设备示例：HIK 2bdf:0101

Configuration 1
    │
    ├── Interface 0 (Video Control) — bInterfaceNumber=0
    │   ├── EP0   ← 共用（控制传输——XU 命令走这里）
    │   └── EP83  ← 私有（IN, Interrupt, 16B — 设备状态通知）
    │
    ├── Interface 1 (Video Streaming) — bInterfaceNumber=1
    │   ├── EP0   ← 共用 (同一个 EP0！)
    │   │
    │   ├── Alternate 0: 零带宽 (关流)
    │   │   └── EP81 (IN, Bulk, 512B)
    │   ├── Alternate 1~8: 等时 (开流后取数据)
    │   │   └── 复用 EP81 (IN, Isochronous)
    │   │         └── Alt 不同 = 端点号相同但传输模式变了
    │   └── (同时只有一个 Alt 激活)

USB View 验证：

Used Endpoints: 3              ← EP0 + EP 0x83 + EP 0x81
    Number of open Pipes: 2        ← 用户态只看到 2 个数据管道 (EP0 不算)
    Pipe[0]: EP3  IN  Interrupt    ← 属于 IF=0 (VC)
    Pipe[1]: EP1  IN  Bulk         ← 属于 IF=1 (VS)

描述符树中的层级

Device Descriptor
     └── Configuration Descriptor
          ├── Interface Descriptor (IF=0, VC)
          │    ├── VC Header / Input Terminal / Processing Unit
          │    ├── Extension Unit (bUnitID=0x0A)    ← XU 在这里

libusb 中的体现

操作走哪个端点libusb 调用
发 XU 命令 EP0 libusb_control_transfer(devh, 0xA1, 0x85, wVal, wIdx, ...)
wIndex = (XU_ID<<8) | VC_IF   ← 指定 Interface

bmRequestType=0x01(Standard)   ← 不是 Class！

Alternate Setting 的直观理解

同一个 Interface 的不同 Alternate Setting = 同一扇门的不同开法：

Alternate含义端点状态什么时候用
Alt 0零带宽无数据端点关流（默认状态）
Alt 1批量传输EP81 激活 (Bulk)取流（靠谱但慢）
Alt 2~N等时传输EP81 重新定义 (Isoch)取流（快但不靠谱）

SET_INTERFACE 切换到 Alt 1+ = 开流；切回 Alt 0 = 关流。端点号一样（EP81），但传输类型和数据量变了。

2.7 ⛁ 逐比特 Token 包逐位解析

IN/OUT/SETUP Token (24 bits)

SYNC(8b) | PID(8b) | ADDR(7b) | ENDP(4b) | CRC5(5b) | EOP(3b)

SYNC字段 (8 bits)

00000001 (0x80, LSB first)。7个0→NRZI连续7次跳变→接收方PLL锁定时钟。最后1→停止跳变→标志SYNC结束。

ADDR字段 (7 bits)

范围 0x00~0x7F (0~127)。0x00 = 默认地址，0x01~0x7F = 可分配地址(127个)。

ENDP字段 (4 bits)

范围 0~15。方向由PID决定(IN PID=读, OUT PID=写)。EP3 IN和EP3 OUT是硬件上两个不同的FIFO。

CRC5字段 (5 bits)

多项式: G(x) = x⁵ + x² + 1 (100101 = 0x25)。校验范围: ADDR(7b) + ENDP(4b) = 11 bits。

Token 包 (IN/OUT/SETUP)

SOF Token (结构不同)

SYNC(8b) | PID=SOF(0xA5) | Frame Number(11b) | CRC5(5b) | EOP

Frame Number: 0~2047。FS: 1帧=1ms→~2秒回卷。HS: 1微帧=125μs→256ms回卷。

2.8 ⛁ 逐比特 Data 包逐位解析

结构

SYNC(8b) | PID(8b) | DATA(0~1024B) | CRC16(16b) | EOP(3b)

CRC16

多项式: G(x) = x¹⁶ + x¹⁵ + x² + 1。截断多项式: 0x8005。校验范围: DATA字段全部字节。

短包终止

如果数据长度 < MaxPacketSize → 短包 = 传输结束信号。如果恰好等于MaxPacketSize → 追加零长度DATA包标记结束。

DATA0/DATA1翻转机制

  • 初始化: Toggle = DATA0
  • 成功(收到ACK): Toggle翻转
  • NAK: Toggle不变
  • 接收方检测到Toggle与预期不一致→知道是重传→回ACK但丢弃数据

Data 包 (DATA0/DATA1/DATA2/MDATA)

2.9 ⛁ 逐比特 Handshake 包逐位解析

结构（USB最短的包）

SYNC(8b) | PID(8b) | EOP(3b)

没有DATA、没有CRC。PID自身的高4位=~低4位校验已足够。

ACK (0xD2)

1101 0010 — 数据被正确接收。发送方翻转Toggle，事务完成。

NAK (0x5A)

0101 1010 — 暂时忙/无数据。Toggle不翻转。NAK总是Device给Host的。不是错误，是正常流控。

STALL (0x1E)

0001 1110 — 端点Halted或请求不支持。NAK="等等再来" vs STALL="别试了，需要人来修"。

NYET (0x96, HS only)

1001 0110 — HS批量OUT: 数据收了但FIFO满了。PING协议的一部分。

🔑 ACK vs STATUS：两层确认机制 为什么 ACK 不够，还需要 STATUS？

这是 USB 协议设计中最容易被误解的地方——ACK 和 STATUS 是不同层级的两回事：

ACKSTATUS
层级包级（硬件自动）传输级（软件语义）
谁发接收方收到每个数据包后都回控制传输发起方关账时发
含义"CRC 对了，比特传对了""这笔交易结束了，可以归档"
承载方式Handshake 包（PID=0xD2）零长度 DATA 包 + 反向 Token
出现在哪种传输所有传输（等时除外）仅控制传输
如果缺失发送方重传该包对方不知道这笔交易算不算完

类比：快递扫码 vs 合同盖章。ACK = 快递员每件扫码确认包裹没摔坏（每个包都扫）；STATUS = 收件人在回执单上签字，合同达成并归档（只签一次）。控制传输的 DATA 阶段可能有多个包，每个包都有 ACK，但 STATUS 只做一次——它的意义不是"最后一个包收到了"，而是"这笔 SETUP 发起的交易完成了"。

为什么两个都要？Host 完全可能在 ACK 了一个 DATA 包之后，又发另一个 SETUP 中止这笔传输。ACK 一个包 ≠ 满意整笔交易。STATUS 才是 Host 明确说"交易完成"的唯一方式。两者缺一不可：没有 ACK 包传输不可靠，没有 STATUS 控制传输的语义不完整。

🔌 实战：批量传输的 payload 里为什么也有 SETUP 格式？ 厂商的"拿来主义"——把 EP0 那套搬到批量端点

不是 USB 规范要求的——是厂商自己抄过去的。

USB 规范层面：控制传输 SETUP 包有 8 字节固定格式；批量传输是纯数据管道，爱发什么发什么。但实际设备中，你经常在 Bus Hound 里看到批量传输的 payload 前 8 字节长得和 SETUP 包一模一样：

Bulk OUT  0x03  12B    A1 81 00 04 00 0A 04 00 [32 2E 30 00]
                           ↑── 跟 SETUP 包完全一样的 8 字节 ──↑ ↑ payload ↑

为什么？一句话——代码复用：

EP0 控制传输批量端点模拟
并发一次一个，等 STATUS 完✅ 多个命令异步执行
数据量wLength 最大 64KB，HS 每包 64B✅ 512B/包，多大都行
排队必须等上一笔 STATUS 闭环✅ 可以 pipeline
代码复用—✅ 直接复用 EP0 命令解析代码

这算违反规范吗？不算。规范只规定 EP0 必须用那 8 字节头，没有禁止其他端点模仿。批量端点是"纯数据管道"——数据里的格式是厂商的自由。TCP 没有禁止你在 payload 里传 HTTP，同理 USB 没有禁止批量端点模仿 SETUP 格式。

Bus Hound 怎么看穿？控制传输的 CTL 行帮你展开了字段名；批量传输的 Bulk 行就是一坨 hex。当你能从一坨 hex 里认出 A1 81 = UVC GET_CUR + CS_ID 时——USB 协议已经入门了。

⚖️ STATUS 不是"锦上添花"——是拒绝的唯一入口 SETUP 必须 ACK、DATA 可能不存在 → 拒绝只能发生在 STATUS

STATUS 是不可或缺的协议硬需求。理解为什么，先看三个约束：

  1. SETUP 阶段设备必须 ACK（见 2.17）——硬件自动清状态机、强制 DATA0，不能在这里说"不支持"
  2. DATA 阶段不一定有——如果 wLength=0，DATA 阶段直接跳过
  3. EP0 是共享资源——Host 必须知道"这笔完了，可以发下一个 SETUP"

三条加在一起：SETUP 拦不住拒绝，DATA 可能不存在 → 拒绝唯一能发生的地方就是 STATUS。

SETUP:  "给我不存在的描述符 #99"
           Device → ACK     ← SETUP 必须 ACK，不能拒绝
    DATA:   无数据（或回了也是错的）
    STATUS: Device → STALL  ← ❌ 拒绝唯一发生在这里！
           或
           Device → ACK     ← ✅ 交易成功

    对比批量传输——没有 STATUS 阶段，每个包都可以直接回 STALL:
    OUT Token → DATA → STALL  ← 当场拒绝，不需要 STATUS

三段式不是冗余——是权力分立：

阶段角色可以拒绝吗？
SETUP提出请求❌ 必须受理（硬件强制）
DATA提供数据— 可选，可能不存在
STATUS宣布判决✅ ACK=成功 / STALL=驳回

去掉 STATUS，设备对不支持的 SETUP 命令连说"不"的权利都没有。这就是为什么上方的 SVG 里 STATUS 不是可选项——三阶段里它才是最终裁决者。

三种类型

  1. 控制读(Read): SETUP→DATA(IN)×N→STATUS(OUT)
  2. 控制写(Write): SETUP→DATA(OUT)×N→STATUS(IN)
  3. 无数据(No Data): SETUP→STATUS(IN)

帧内优先级

    HS: 先PING探测空间→ACK→再OUT→避免浪费

    PING流程:
    Host→PING Token→Device回ACK(有空间)/NAK(满)
    ACK→OUT Token+DATA→Device回ACK/NYET
    NYET: 数据收了但满了，下次先PING再发

理论吞吐

  1. 客户端指定了传输长度
  2. 短包终止 (< MaxPacketSize)
  3. 零长度包 (设备不想NAK)

基本结构（无握手包！）

IN:  Host→IN Token ←DATA (结束!)
    OUT: Host→OUT Token→DATA (结束!)

没有ACK, 没有NAK, 没有STALL。

为什么不要握手

实时>可靠性: 30fps视频(33ms/帧), 重传延迟比丢几帧更致命。人脑对5-10%帧丢失不敏感，但对>50ms延迟非常敏感。

    IN+DATA2(1024B)→IN+DATA1(1024B)→IN+DATA0(1024B)

  • 01=Adaptive (自适应, 如USB话筒)

SOF包结构

SOF是广播包(没有ADDR/ENDP)，总线上所有设备都收到。

Frame Number = 0~2047

    HS: 1微帧=125μs→每125μs发SOF→但Frame Number每1ms才+1

2.17 为什么 SETUP 事务必须 ACK，不能 NAK？

SETUP 是控制传输最特殊的阶段——设备不能用 NAK 拒绝。先看对比：

正常 OUT（可NAK）:
      Host→OUT Token→DATA0→设备回 NAK("忙")
      Host 稍后重试→OUT Token→DATA0→设备回 ACK("收到")
      重试是安全的——数据还是那些数据

    SETUP（不可NAK）:
      Host→SETUP Token→DATA0(8B Setup Packet)→设备必须 ACK
      如果设备可以 NAK→Host 重试→但 SETUP ="开始新控制传输"
      →第一次 SETUP 已触发状态机转移→第二次 SETUP 是什么？语义混乱

三个根因

① SETUP = 状态机清零信号：SETUP Token 一到达，USB 硬件自动做两件事：清空之前未完成的控制传输状态；强制复位 Data Toggle（SETUP 永远用 DATA0）。SETUP 是 Hard Reset——不仅带命令，还隐含"之前的事一笔勾销"。如果允许 NAK，硬件就得维护"挂起的 SETUP"状态来记住刚才有个 SETUP 没处理完，这跟清零信号设计自相矛盾。

② EP0 硬件保证——SETUP 缓冲永远可用：USB 规范在硅片层面做了保证：EP0 必须预留专用 SETUP 缓冲区（8 字节 FIFO，恰好容纳一个 Setup Packet），这个缓冲区跟普通数据 FIFO 分离。固件来不及取走时硬件也能接收，绝不会"缓冲区满"。就像每个 USB 设备的 EP0 都有一个"永远不上锁的 SETUP 信箱"——邮差随时可投递。

③ USB 协议不允许 SETUP 重试的语义：NAK ≠ 无响应。NAK = "包正确但我忙"。但控制请求很多不是幂等的（如 SetConfiguration()——第二次 Set 同一个配置是什么行为？），重试制造歧义。USB 规范第 9 章明确规定 SETUP 阶段的 DATA0 包不能被 NAK 拒绝。如果设备检测到 CRC 错误，应静默丢弃不回应（超时），而非 NAK。

SETUP 异常处理

情况设备行为Host 处理
SETUP 包 CRC 校验错静默丢弃（不响应）超时，判定总线错误，重发 SETUP 事务
SETUP 正确、但设备不支持该命令DATA 阶段正常走完，STATUS 阶段返回 STALL收到 STALL，知道"设备不支持"
SETUP 正确、固件来不及处理硬件自动 ACK（不依赖固件）继续发送下一事务

关键：即使设备不支持 SETUP 里的命令，SETUP 阶段本身也照样 ACK。拒绝在 STATUS 阶段用 STALL 表达——"命令我听懂了，但我不支持/做不到"。

这解释了为什么 STATUS 不是锦上添花：SETUP 必须 ACK、DATA 可能不存在——控制传输的三段式设计把唯一能表达"不支持"的地方留给了 STATUS。详见 2.10 的折叠区「⚖️ STATUS 不是"锦上添花"」。

2.19 127 个设备一帧照顾得过来吗？

ADDR = 7 bit → 最多 127 个设备。但如果 127 个设备同时有数据，一帧能搞定吗？

📊 展开完整分析 理论极限 × 现实制约 × 硬约束

理论极限：127 个最小事务能塞进一帧吗？

FS（12Mbps）下，一帧 = 1ms = 12,000 bit times。

一个最小事务（IN Token → NAK）只需：

IN Token:  SYNC(8) + PID(8) + ADDR(7) + ENDP(4) + CRC5(5) + EOP(3) ≈ 35 bit times
    NAK:       SYNC(8) + PID(8) + EOP(3)                              ≈ 19 bit times
    总线间隙/翻转                                                       ≈  6 bit times
    合计:                                                               ≈ 60 bit times

127 个设备各问一句（全 NAK，纯点名式轮询）：

127 × 60 + SOF(35) ≈ 7,655 bit times → 占 64%，理论上还有余量

但纯 NAK 毫无意义——有数据立刻爆

事务类型典型大小单次耗时127 设备总耗时
IN + NAK0B~60 bit times~7,655 ✅
IN + DATA + ACK（鼠标 8B）8B~200 bit times~25,400 ❌ 2帧+
批量 OUT + 512B + ACK512B~4,300 bit times~546,000 ❌ 45帧
等时 IN + 1023B（无握手）1023B~8,400 bit times❌ 一个占 70%

一个 U 盘发 512 字节，13 个类似设备就能吞掉一整帧。

带宽分配机制（USB 的真正防线）

一帧带宽 = 100%
    ├── 等时/中断：Host 控制器预留"固定时段"
    │   └── 规范要求预留 ≤ 90% 给等时+中断（FS）
    ├── 批量/控制：吃剩饭（等时+中断剩下的才给）
    │   └── 如果等时吃掉 80%，批量只剩 20%
    └── SOF 开销：每帧 ~35 bit times

关键：Host 在枚举阶段就会算账。当设备声明"我是等时设备，每帧要 800 字节"，Host 的带宽管理器检查剩余带宽。如果不够，直接拒绝配置（SetConfiguration 失败）。所以根本不会出现"127 个设备都配好然后帧爆"——Host 在分配时就拦住了。

其他硬约束

约束瓶颈
供电Root Hub 只出 500mA，127 个 Bus-powered 需要 12.7A——物理上不可能不靠外部供电 Hub
Hub 层级USB 最多 5 层 Hub，127 个地址包括 Hub 自身
Host 控制器多数控制器硬件调度表只能容纳几十个并发传输
实用场景鼠标键盘 bInterval=10ms（每 10 帧才应答一次），U 盘只在传文件时活跃——大部分时间大部分设备在静默

结论

127 是地址空间的上限，不是并发能力的承诺。ADDR 7 bit 给你 127 个 IP 地址——但不保证 127 个设备同时满速通信。USB 靠的是"多数设备多数时间不说话"假设，而不是"每帧问候所有设备一遍"的设计。真需要 127 个等时设备并发流数据，USB 不是该用的总线。

FUNC_SWITCH 设计约束

  • 切换先于读写：每次 GET_LEN / GET_CUR / SET_CUR 之前必须调用 FUNC_SWITCH。固件内部维护一个"当前激活的 {CS_ID, SubFunc}"寄存器。
  • 幂等性：如果上一个请求已经切到同一对 {CS_ID, SubFunc}，再次切换是安全的——固件应设计为"相同则不重复初始化"。
  • 错误处理：FUNC_SWITCH 成功后，SET_CUR 返回的 STATUS 可能是 STALL（功能不支持）；也可能是 ACK 但错误码寄存器非零。两者都检查才算完整校验。
  • GET_LEN 返回 2 字节 LE：统一协议规则——任何 CS_ID 的 GET_LEN 都返回 2 字节 uint16 LE，表示该功能（当前 SubFunc）的参数字节长度。0 表示无参数。

坑 5：忘记 detach 内核驱动 → claim 失败 
// Linux 上的正确生命周期:
    libusb_init(&ctx);
    devh = libusb_open_device_with_vid_pid(ctx, vid, pid);

    if (libusb_kernel_driver_active(devh, if_num))
        libusb_detach_kernel_driver(devh, if_num);   // 解绑 uvcvideo

3.1 描述符层级关系

USB 设备靠描述符向 Host 自报家门。所有描述符组成一棵严格的树：

Device Descriptor（1个）→ Configuration（≥1）→ Interface（≥1）→ Endpoint（0~N）
    └── 每个描述符前 2 字节铁律: bLength + bDescriptorType

层级约束

层级数量说明
Device1 个仅一个
Configuration≥1 个多配置=多功耗模式
Interface≥1 个复合设备有多个
Endpoint0~N 个不含 EP0

描述符链内存布局

Host 用 Get_Descriptor(Configuration) 一次性读回整条链——Config + Interface + Endpoint + 类专用全串联在一起。靠 bLength 当链表的 next 指针，wTotalLength 声明总长。

MQTT 类比

USBMQTT
Device DescriptorCONNECT 报文（Client ID、协议版本）
ConfigurationTopic 权限声明
InterfaceTopic QoS 定义
EndpointTCP 连接参数
bLength+bDescriptorTypeFixed Header byte 0（决定整体解析方式）
📊 端点和接口有什么区别？

类比：一个 U 盘 — Interface 0: Mass Storage（"我是存文件的"），Endpoint 1 IN + Endpoint 2 OUT（数据大门）。接口 = 功能，端点 = 管道。

维度EndpointInterface
本质硬件 FIFO逻辑功能分组
包含关系属于某 Interface包含多个 Endpoint
标识bEndpointAddressbInterfaceNumber

复合设备示例：键盘+触摸板 → Interface #0=键盘(EP1 IN) + Interface #1=触摸板(EP2 IN)，两个功能各用各的端点。

📊 怎么知道这个接口能干什么？

Interface Descriptor 用三个字段精确回答：

bInterfaceClass      → "大类是什么" (如 0x03=HID, 0x02=CDC, 0x0E=Video)
    bInterfaceSubClass   → "大类下的哪个子类" (如 HID Boot=0x01)
    bInterfaceProtocol   → "用什么协议变体" (如 Mouse=0x02, Keyboard=0x01)

三级分类共同定位到驱动。Host 加载链：Class→系统加载类驱动→SubClass+Protocol→创建设备节点。这就是为什么 U 盘插上自动有盘符——操作系统内置了标准类驱动。

3.3 bcdUSB 的 BCD 编码细节

BCD = Binary-Coded Decimal：每个 nibble（4 bit）表示一个十进制数字（0~9）。

bcdUSB = 0xJJMN → JJ=主版本, M=次版本, N=子次版本
    0x0200 = USB 2.0    0x0110 = USB 1.1
    0x0300 = USB 3.0    0x0310 = USB 3.1    0x0320 = USB 3.2

⚠️ 三个坑

坑错误正确
当整数读0x0110=272 ❌nibble 拆开→1.1.0→USB 1.1 ✓
直接比较bcdUSB >= 0x0110 碰巧work但不严谨拆 nibble：major=(bcdUSB>>8)&0xFF
bcdUSB vs bcdDevice把固件版本当协议版本bcdUSB=协议版本，bcdDevice=固件版本（厂商自定）

所有 USB 版本号都用 BCD：bcdUSB、bcdDevice、bcdHID、bcdCDC 等。

📊 端点能被多个接口共享吗？UVC 摄像头接口长什么样？

端点独享原则：每个端点只属于一个接口。唯一例外是 EP0，全局公有。

UVC 典型布局：

Interface #0 (VC): bInterfaceClass=0x0E, Sub=0x01, Alt=0
      └── EP3 IN (中断) ← 硬件状态通知（可选）

    Interface #1 (VS): bInterfaceClass=0x0E, Sub=0x02
      ├── Alt=0: bNumEndpoints=0 ← 零带宽，默认激活
      ├── Alt=1: EP2 IN (等时) ← 640×480 MJPG
      └── Alt=2: EP2 IN (等时) ← 1280×720 MJPG

摄像头关闭时激活 Alt 0（零带宽），打开时切到 Alt 1~N。同一时刻只激活一种分辨率——Alternate Setting 保证了互斥。

⛁ 3.6 Endpoint Descriptor — 7 字节逐位

描述符树最底层：数据从哪个门走、朝哪边、一次搬多少、多久查一次。

00x07bLen
10x05Type
20x82Addr
30x03Attr
4-50x0008wMaxPkt
60x0AbInt

bEndpointAddress (byte 2) 位拆解

Bit 7    = 方向: 1=IN(Dev→Host), 0=OUT(Host→Dev)
    Bit 6-4  = 保留=0
    Bit 3-0  = 端点号 0~15

    0x82 = 1000 0010 → EP2, IN   0x01 = 0000 0001 → EP1, OUT

bmAttributes (byte 3) 位拆解

Bit 1-0 = 传输类型: 00=控制 01=等时 10=批量 11=中断
    （等时端点 Bit3-2=同步类型, Bit5-4=用途）

    0x03=中断(HID)  0x02=批量(U盘/CDC)  0x05=等时Async(UVC)  0x0D=等时Sync(音频)

wMaxPacketSize (byte 4-5)

FS: 批量≤64, 中断≤64, 等时≤1023。HS: 批量=512, 中断/等时≤1024。HS 高 2 bit 挪用为每微帧事务数（1/2/3）。LE!

bInterval (byte 6)

见 3.7——同一个值在 FS/HS×中断/等时 下有四种不同解读。

HEX 示例

鼠标 HID 中断 IN: 07 05 81 03 08 00 0A → EP1 IN, 中断, 8B, 10ms
    U盘批量OUT:        07 05 02 02 40 00 00 → EP2 OUT, 批量, 64B, 忽略

3.7 bInterval 在不同速率下的含义

最容易被误解的字段——同一个值在不同速率/传输类型下含义完全不同。

速率传输公式单位示例
FS中断bIntervalms10→10ms (100Hz)
LS中断bIntervalms10~255ms
FS等时2^(bInterval-1)帧(ms)1→1ms, 2→2ms, 3→4ms
HS中断2^(bInterval-1)微帧(125μs)4→8μf=1ms
HS等时bInterval-1微帧(125μs)1→每微帧
全部批量忽略—有空就来

⚠️ 注意

HS 中断是指数、HS 等时是线性，搞反了等时间隔会从 μs 级暴涨到秒级。bInterval=4 在 HS 中断 = 1ms，等效 FS 中断的 bInterval=1——数值不同但效果相同。

⛁ 3.8 String Descriptor

唯一对人类友好的描述符——UTF-16LE UNICODE 编码，存产品名/制造商/序列号。

Offset 0: bLength (可变)  1: bDescriptorType=0x03  2~N: bString (UTF-16LE)

String #0 是特例

存语言 ID 列表 (LANGID)，如 0x0409=English。Host 必须先读 #0 知道有哪些语言，再带着 langid 读 #1/#2/#3。

Unicode 编码示例

"Ultra Fit"→ HEX: 55 00 6C 00 74 00 72 00 61 00 20 00 46 00 69 00 74 00
    每个字符 2 字节 (UTF-16LE), 英文=0x00+ASCII码, 中文=UTF-16码点
    '视'(U+89C6)→C6 89 (LE), '频'(U+9891)→91 98

3.10 BOS Descriptor — USB 3.x 扩展容器

Device Descriptor 只有 18 字节无法扩展。BOS 用 TLV 链表方式追加新能力声明。

BOS Header (5B): bLength(5)+bDescType(0x0F)+wTotalLength+bNumDeviceCaps
    每个 Capability: bLength+bDevCapabilityType+Capability数据...

    USB 2.0 Extension (LPM): Type=0x02, bmAttributes bit0=1→支持LPM链路电源管理
    SuperSpeed USB:          Type=0x03, 宣告最低工作电压/速度
    Container ID:            Type=0x04, 128-bit UUID 唯一标识
    SuperSpeedPlus:          Type=0x0A, USB 3.1+ 超高速参数
