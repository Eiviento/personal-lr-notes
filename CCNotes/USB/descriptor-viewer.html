🔍 关键字段深入

bDeviceClass = 0xEF 而不是 0x0E：为什么要"绕路"？

USB spec 规定：如果设备在 Device Descriptor 层面声明了设备类（如 0x0E=Video），那么该设备的所有 Interface 都必须属于该类。但我们的设备 3 既有 Camera (Video) 又有 Audio，是复合设备。即使设备 1&2 只有 Video，海康也统一用了 IAD 模式——这是现代 USB 复合设备的最佳实践。

bDeviceClass=0xEF + bDeviceSubClass=0x02 + bDeviceProtocol=0x01 的组合告诉 Host："别在 Device 层面判断我的类型，去读 IAD Descriptor。"

好处：每个 Interface 可以有自己的 Class/SubClass/Protocol，由 IAD 将多个 Interface 绑定为一个"功能"。例如 UVC 摄像头 = VC Interface + VS Interface，由 IAD 声明这两个是一体的。

bMaxPacketSize0 = 0x40 (64 字节)：HS 设备的"硬编码"选择

EP0 是控制端点，用于枚举阶段的描述符请求和标准请求。USB 2.0 spec 规定：

  • FS 设备：EP0 最大包可选 8、16、32 或 64 字节
  • HS 设备：EP0 最大包固定 64 字节

为什么 HS 固定 64？因为枚举阶段 Host 还不知道设备速度（枚举第一步就是读 Device Descriptor 前 8 字节来判断），HS 设备在这之前就已经被 Hub 检测为 HS 了，Host 直接用 64 字节包通信。

VID/PID 的 Little-Endian 陷阱

USB 描述符中所有多字节字段都是 Little-Endian（小端序）。idVendor = 0x2BDF 在描述符中的实际字节序列是 DF 2B（低字节在前）。

这是 USB 新手最容易踩的坑——如果你用 hexdump 看到 DF 2B，不要读成 0xDF2B。

同理：bcdUSB = 0x0200 在字节流中是 00 02，idProduct = 0x0101 是 01 01。

wTotalLength = 433 字节：描述符链的"总账本"

Host 通过 GetDescriptor(Configuration) 一次性读回整个描述符链，长度由 wTotalLength 告知。设备1&2 的 433 字节包括：Config(9) + IAD(8) + Interface(9)×2 + VC Header(13) + Input Terminal(18) + Processing Unit(12) + Extension Unit(29) + Output Terminal(9) + 中断端点(7) + 类专用 0x25 端点(5) + Bulk 端点(7) + VS Input Header(16) + 3 种 Format Type(27+11+28) + 7 个 Frame Type(30×7) + Color Matching(6)。

所以抓包时看到的"配置描述符"请求一次回 433 字节——它其实包含了一整棵描述符树。

bmAttributes bit7 必须为 1：USB spec 的历史遗留

USB spec 规定 bmAttributes 的 bit7 保留且必须置 1。虽然这个 bit 从未被使用，但所有符合 spec 的设备都必须设置它。如果你在抓包时看到 bmAttributes=0x40（bit7=0），那是设备固件的 bug。

bit6=1 表示自供电（有自己的电源适配器），bit5=0 表示不支持远程唤醒（Host 不能通过网络/按键唤醒此设备）。

Device Descriptor 里我们说过：设备层 bDeviceClass=0xEF 只是"绕路"信号。真正的类型声明在 IAD 里——bFunctionClass=0x0E 明确告诉 Host："这个功能是 Video 类"。

设备3 既有 Camera 又有 Audio，是典型的多功能复合设备；即使设备1&2 只有视频，海康也统一用了 IAD 模式。Host 看到 Device Descriptor 的 0xEF/0x02/0x01 后，就知道要去解析 IAD，把 IAD 声明的接口组当作一个整体来加载驱动。

IAD 是 USB 2.0 才加入的描述符：它解决什么问题？

USB 1.x 时代没有 IAD。复合设备只能在 Device Descriptor 里声明一个笼统的类，Host 无法得知哪些 Interface 属于同一个"功能"——比如带摄像头的音箱，Host 不知道 Interface 0 和 Interface 1 是一体的。

USB 2.0 引入 IAD 作为"胶水"：把一段连续的 Interface 粘成一个 Function。Windows 从 XP SP1 开始支持，Linux 从 2.6.4 内核开始支持。如今几乎所有的 UVC 摄像头 + UAC 麦克风复合设备都用它。

VC 接口 = 摄像头的"遥控器"：控制走 EP0，为什么还要中断端点？

Video Control 接口不传输视频数据，职责是控制：曝光、白平衡、增益、变焦……这些操作通过 UVC 类专用请求（GET_CUR / SET_CUR 等）在 EP0 上完成，走控制传输。

但有些事件是摄像头主动发起的——例如自动曝光调节完成、按键被按下。这些异步事件不能等 Host 轮询，于是用中断传输"敲门"：Host 收到中断通知后，再用控制请求读取详情。

bAlternateSetting：同一接口的"档位"切换

一个 Interface 可以有多个 alternate setting（备选设置）。枚举阶段 Host 看到的是 alt 0；需要开始传输时，Host 用 SetInterface(interface, alt) 切换到其它档位。

VS 接口的常见用法：alt 0 不分配带宽，alt 1..n 逐级增加端点带宽——空闲时不占总线，需要传输时才"租用"。VC 接口一般只有一个 alt 0。

VS 接口 = 视频数据的"运输队"：Payload 全走 Bulk IN

Video Streaming 接口负责把视频帧搬运给 Host。设备1&2 用的是 Bulk IN（EP1）——UVC 1.1 允许等时或 Bulk 两种选择，海康选了 Bulk：视频数据量大且丢包不可容忍（一帧坏块 = 花屏），Bulk 的 CRC 校验 + 自动重传保证数据完好。代价是延迟不固定——好在预览场景对延迟不敏感。

设备1&2 的 VS 接口挂在 alt 0 上就有 1 个 Bulk 端点（EP1）；而 VS 的完整 298 字节类专用链（Input Header + 3 种 Format + 7 个 Frame + Color Matching）将在 Task 6 的类专用描述符章节拆解。

VS 接口之后：0x24 描述符的 Format → Frame 两级结构

每个 VS 接口后面跟着一长串类专用描述符：Input Header (0x24, 0x01) → N 个 Format Type（Uncompressed 0x04 / MJPEG 0x06 / Frame Based 0x10）→ 每个 Format 下挂多个 Frame Type（0x05 / 0x07 / 0x11）→ 最后 Color Matching (0x0D)。

设备1&2 的 VS 链共 wTotalLength=0x012A (298B)：Input Header(16) + YUY2 Format(27) + 3 个 Frame(90) + MJPEG Format(11) + 3 个 Frame(90) + H.264 Format(28) + 1 个 Frame(30) + Color Matching(6)。

bInterval 的单位取决于端点速度（USB 2.0 spec 9.6.6）：

  • High-Speed：bInterval = 2^(n-1) × 125μs。n=8 → 2^7 × 125μs = 16000μs = 16ms（设备1&2 当前运行在 HS）
  • Full-Speed：bInterval = n × 1ms。n=8 → 8ms（设备2 Other Speed Config 揭示的值）

设备2 的 dump 里两个速度都出现了：HS 状态解析为 "128 microframes → 16 ms"，Other Speed（FS）下同一个 0x08 解析为 "8 ms"。设备1 的 Device Qualifier 请求失败（D3 低功耗状态，ERROR_GEN_FAILURE），所以只有设备2 暴露了这个细节。

0x83 怎么读：bEndpointAddress 的位域解码

0x83 = 1000 0011b：bit7=1 → 方向 IN（设备 → Host）；bits 6-4 = 000 → 保留；bits 3-0 = 0011 → 端点号 3。所以 0x83 = "EP3, IN"。

对照设备2 的管道信息：Pipe[0]: EndpointID=3, Direction=IN, Type=Interrupt, wMaxPacketSize=0x10, bInterval=8 → 2160 Bits/ms，完全一致。

另外，这个中断端点后面还紧跟一个 5 字节的类专用描述符：0x25, subtype=0x03, wMaxTransferSize=0x0010——它告诉 UVC 驱动每次事件报告最多 16 字节。

设备1&2 平时挂在 HS 端口上，wMaxPacketSize=0x0200（512B）。但设备2 的 dump 里还有一份 Other Speed Configuration——如果这台设备被插到只有 Full-Speed 的 Hub 后面，同样的 Bulk IN EP1 的 wMaxPacketSize 会变成 0x0040（64B）。

原因：USB 2.0 spec 规定 Bulk 端点最大包在 HS 为 512B，在 FS 最大只有 64B。设备必须为每种速度准备一套配置（Host 通过 GetDescriptor(Other_Speed_Configuration) 读取），这就是上表设备2 列被标黄的原因。

对比：中断端点 16B 在 HS/FS 都合法，所以无需变化；而 Bulk 端点必须"降级"。设备1 的 Device Qualifier 请求失败（D3 状态），所以只有设备2 暴露了这个细节。

视频数据为什么走 Bulk，而不是等时 (Isochronous)？

等时传输保证带宽和时序，但不保证数据正确（没有重传）；Bulk 恰好相反——带宽不保证，但通过 CRC 校验 + 错误重传保证数据完好。

UVC 1.1 的 VS 接口两种都允许。海康选了 Bulk：视频帧损坏无法接受（一帧花屏影响观感），而 HS 480Mbps 带宽对 640×360@30fps MJPEG（约 13.8 MB/s ≈ 110 Mbps）绰绰有余。设备2 管道信息印证：Pipe[1]: Type=Bulk, wMaxPacketSize=0x200, bInterval=0。

⚠️ bInterval=0 对 Bulk 无意义——spec 规定 Bulk 端点忽略此字段，只有 Interrupt/Isochronous 才使用它。

类专用描述符 — 0x24/0x25 分发机制

标准描述符只解决"骨架"问题；摄像头怎么控制、支持哪些格式，由类专用描述符回答。而它们靠同一个类型码 + 上下文分发。

🧭 bDescriptorType = 0x24 / 0x25 的分发原理

UVC 的类专用描述符大量复用同一个 bDescriptorType，含义由所在接口的 bInterfaceSubClass 决定：

bDescriptorType = 0x24 (Video Control Interface)
   └─ 由"所属接口的 bInterfaceSubClass"决定含义
        ├─ 接口 subclass = 0x01 (VideoControl)  →  VC 类描述符
        │     0x01 VC Header          0x02 Input Terminal
        │     0x03 Output Terminal    0x04 Selector Unit
        │     0x05 Processing Unit    0x06 Extension Unit
        └─ 接口 subclass = 0x02 (VideoStreaming) → VS 类描述符
              0x01 VS Input Header     0x04 Uncompressed Format
              0x05 Uncompressed Frame  0x06 MJPEG Format
              0x07 MJPEG Frame         0x0D Color Matching
              0x10 Frame-Based Format  0x11 Frame-Based Frame

bDescriptorType = 0x25 (Video Control Endpoint)  → 只出现在 VC 接口下
       0x03 Interrupt（VC 中断端点的类专用信息）

bDescriptorType = 0x26 (Video Streaming Endpoint) → 只出现在 VS 接口下（本设备未用）

为什么可以复用同一个类型码？——靠上下文区分，不靠类型码本身

因为解析上下文不同：Host 遍历描述符链时，先读到接口描述符（0x04），知道当前处于哪个接口（subclass 是多少），之后遇到的 0x24 就按该接口的语义解析。这就像 MQTT 里同一个 topic 名在不同层级（camera/ctl/ 与 camera/data/）承载不同类型报文。

这也意味着：类专用描述符必须紧跟所属接口描述符（以及紧随其后的端点描述符），链的顺序不能乱。顺序乱了，0x24 就会解析到错误的含义。

0x02DC6C00 = 48,000,000 ✓。但在字节流里以小端序存放：低字节在前 → 实际看到的 4 个字节是 00 6C DC 02。用 hexdump 看时不能直接读成 0x00 6C DC 02，要"倒过来"组合成 0x02DC6C00。

wTotalLength = 81 字节的验算

注意：不含端点描述符与 0x25——0x25 属于"类专用端点描述符"，不算在接口描述符子链里。Host 靠 wTotalLength 知道 VC 子链到哪里结束，好接着找下一个描述符。

bcdUVC = 0x0110：版本决定解析规则；bInCollection 把 VC 与 VS 绑在一起

bcdUVC = 0x0110 表示设备实现 UVC 1.1（UVC 1.5 会写 0x0150）。版本决定 Host 按哪版规范解析后续描述符——不同版本的同号描述符可能有字段差异。

bInCollection = 1 + baInterfaceNr[1] = 0x01 声明"我的数据流搭档是接口 1"。这是 UVC 1.0/1.1 把 VC 与 VS 关联起来的机制（UVC 1.5 改用 bcdUVC + VS 的 bTerminalLink 反查）。Host 据此知道"控制接口 0 管着流接口 1 的摄像头"。

HS→FS 降级备胎机制：Device Qualifier + Other Speed Configuration

USB 2.0 设备可能被插到不同速度的端口上：插在 HS 口跑 480 Mbps，插在老 FS 口（或 Hub 不支持 HS）就只跑 12 Mbps。设备的大多数描述符（类码、字符串等）与速度无关，但端点参数与速度强相关：

  • Bulk 端点最大包长：HS = 512 B，FS = 64 B；
  • bInterval 的换算公式：HS = 2^(n-1) × 125 µs，FS = n ms；
  • 等时端点的每微帧附加事务数：只有 HS 才有。

如果等速切换时让 Host 重新枚举（Reset + SET_ADDRESS + 重读全部描述符），既慢又浪费。于是 USB 2.0 设计了两个"备胎"：

  1. Device Qualifier (0x06, 10 字节)：告诉 Host "如果我在另一速度运行，设备描述符会怎么变"。字段与设备描述符基本一致，其中 bNumConfigurations = 另一速度下的配置数（设备2 = 1）。只有能跑双速的设备才有资格应答；单速设备必须 STALL 该请求。
  2. Other Speed Configuration (0x07, 433 字节)：整条配置链的"另一速度版本"。结构、长度、接口、类描述符完全一样，只有端点参数按另一速度重写（设备2：Bulk 512→64，中断间隔换算基准 125µs→1ms）。

Host 的典型用法：设备以 HS 枚举完成后，Host 发 GetDescriptor(Device_Qualifier) 拿到另一速度信息；如果后面设备被移到 FS 端口，Host 请求 Other_Speed_Configuration，直接按备胎链配置设备，无需重新枚举。

设备1 的 Qualifier 抓取失败是时机问题，不是设备缺陷

设备1 的 Qualifier 抓取失败：抓包时设备处于 D3 低功耗态，控制请求没有得到有效应答（ERROR_GEN_FAILURE），不是设备不支持。

这也提醒你：抓描述符要在设备唤醒状态下抓。

MQTT 类比：Device Qualifier + Other Speed Config 像 MQTT 5 的协商降级（CONNACK 里的 Maximum Packet Size / 版本回退）——设备在不同网络条件下声明不同的能力参数，主协议骨架不变。

⚡ 为什么 2560×1440@30 MJPEG 需要等时端点保证带宽

先算 HS 的带宽硬预算：

HS 等时端点理论上限：每微帧最多 3 个事务 × 1024 B = 3072 B
                    3072 B × 8000 微帧/秒 ≈ 24.6 MB/s ≈ 197 Mbps（含协议开销实际更低）
格式分辨率 @ 帧率需要的带宽结论
YUY21920×1080 @ 520.7 MB/s勉强塞进等时预算（~85%）→ 只能给 5 fps
NV121280×960 @ 1018.4 MB/s同样逼近预算 → 只能给 10 fps
MJPG2560×1440 @ 30压缩后远小于原始 331.8 MB/s只有压缩格式能跑满 30 fps

原始 YUY2 的 2560×1440@30 = 221 MB/s，远超 HS 总线能力，所以无压缩模式只能低分辨率/低帧率；MJPEG 是逐帧压缩，2560×1440 单帧压缩后通常 0.5~2 MB（KS 的 331.8 MB/s 只是按原始位深折算的名义值，不是真实总线流量），30 fps 大约 15~60 MB/s，仍在等时预算内。等时端点保证带宽：每个微帧有固定的事务槽（wMaxPacketSize 位 12..11 的附加事务数声明占几个槽），Host 据此调度，视频帧不会因为总线上的别的事务而延迟。设备1/2 用 Bulk 是因为分辨率低（640×360 以下），Bulk 的重传机制反而更省心；设备3 要做到 2K@30，最可能的设计是等时端点 + 多组 Alternate Setting（每档一个包长）。

为什么接口号是 0 和 2（没有 MI_01 / MI_03）？

UVC 规范要求 VC 与 VS 相邻成对（IAD 的 bFirstInterface..+count 连续），所以视频占用接口 0~1；音频功能接着从接口 2 开始（AC=2, AS=3）。

Windows 只为"功能入口接口"（VC/AC）建节点，VS/AS 被 usbccgp 复合驱动并入，因此设备树里只见 MI_00 与 MI_02——这个"跳号"本身就是 IAD 存在的证据。

音频部分与 UVC 同构：类描述符体系是统一的

设备3 的音频（MI_02）由 usbaudio.sys（UAC 驱动）接管，KS 层只暴露 PCM 16 kHz / 16 bit / 单声道（麦克风采集）。UAC 1.0 与 UVC 的骨架完全同构：

  • bInterfaceClass = 0x01 (Audio) ↔ UVC 的 0x0E (Video)
  • AC 接口 (subclass 0x01 AudioControl) ↔ UVC 的 VC (0x01)
  • AS 接口 (subclass 0x02 AudioStreaming) ↔ UVC 的 VS (0x02)
  • bDescriptorType 0x24 同名同值，靠接口 subclass 分义
  • 描述符链：Input Terminal（麦克风 0x0201）→ Feature Unit → Output Terminal

所以虽然设备3 的原始描述符抓不到，但按 UVC 学的"接口 subclass 分义 + Terminal/Unit 链 + 类型码速查"这套方法，换成 UAC 规范表就能解析。类专用描述符 = 标准骨架 + 每类规范一套"方言"。

常见问题 FAQ

7 个高频疑问——覆盖标准描述符与类专用描述符的常见坑。

❓ 7 个常见问题

Q1: 为什么 bDeviceClass 不直接写 0x0E (Video)？

因为摄像头是复合设备：一个 Video 功能 = VC + VS 两个接口。设备级 class 只能描述"整台设备"，描述不了接口分组。USB 规范规定：凡是用 IAD 做功能绑定的复合设备，设备级必须声明 0xEF (Miscellaneous) / 0x02 / 0x01，把真正的功能分类交给 IAD 的 bFunctionClass=0x0E。

写了 0x0E 反而违反规范——Host 会以为整台设备只有一个接口，直接拒绝加载。

Q2: Alternate Setting 在描述符里怎么体现？

同一接口号出现多个接口描述符：bInterfaceNumber 相同、bAlternateSetting 依次递增（0,1,2…），端点配置不同。Host 用 SET_INTERFACE(接口号, 设置号) 切换。典型 UVC VS 设计：

接口 1, alt 0 : 0 个数据端点（不占带宽）          ← 默认，枚举后先停在 0
接口 1, alt 1 : 等时端点 wMaxPacketSize=512 B     ← 低带宽档
接口 1, alt 2 : 等时端点 wMaxPacketSize=1024 B    ← 高带宽档

应用开视频时，驱动按所选格式挑一档 alt 设置并切换，用完再切回 alt 0 释放带宽。设备1/2 只有 alt 0（Bulk 不需要带宽预留）；设备3（推断）有多档 alt（见 #infer-dev3）。MQTT 类比：同一"主题"（接口）提供 QoS 0/1/2 三档服务，连接时声明用哪档。

Q3: bMaxPacketSize0 对 HS 设备为什么固定 64 字节？

USB 2.0 规范 9.6.1 硬性规定：HS 设备的 EP0 最大包长必须是 64 字节。原因：EP0 是控制通道，控制传输（SETUP + DATA + STATUS）每个事务只能传一个包；64 字节是 HS 下控制事务的标准包长，所有 HS 设备统一，Host 栈的缓冲区与调度器就不用为不同设备准备不同尺寸。

LS=8、FS 可选 8/16/32/64，HS 无选择——统一 64 是规范强制的简化。枚举早期 Host 就是靠这个字段决定后续控制传输怎么切包。

Q4: Device Qualifier 什么情况下 Host 会请求？

USB 2.0 规范 9.6.2：只有能跑双速（HS 与 FS）的设备才有 Device Qualifier；单速设备必须对该请求回 STALL。Host 在设备以 HS 运行时会请求它（拿到"若在 FS 运行会是什么样"的信息）；若设备以 FS 运行而 Host 想知道它的 HS 能力，同样可以请求。

配套的是 Other Speed Configuration（0x07）——另一速度下的整条配置链。典型场景：设备先在 HS 口枚举，之后被插到只支持 FS 的口（或经 FS Hub），Host 不必重新枚举，直接用备胎链配置。设备1 的 Qualifier 抓取失败纯粹是设备处于 D3 低功耗态的抓取时机问题（见 #diff-dev1-dev2）。

Q5: IAD 和 Interface Descriptor 里的 Class 有什么不同？

两者是两个层级的声明：

IAD 的 bFunctionClass接口的 bInterfaceClass
描述对象一组接口（功能）单个接口
设备1 的值0x0E (Video)0x0E (Video)，但 subclass 分 VC(0x01)/VS(0x02)
驱动加载作用决定"这组接口归哪个类驱动管"驱动内部再按 subclass 分派角色
音频功能对照0x01 (Audio)AC 接口 0x01/0x01，AS 接口 0x01/0x02

IAD 是"功能级"的：usbvideo.sys 看到 Video Interface Collection（0x0E/0x03）就绑定整个功能；接口 class 是"接口级"的：VC/VS 的分工靠它。两者分工明确，缺一不可。

Q6: UVC Extension Unit 的 15 个 vendor-specific controls 是干什么的？

设备1/2 的 XU（Unit ID 10）声明 bNumControls=15、GUID {A29E7641-DE04-47E3-8B2B-F4341AFF003B}（海康私有扩展标识）。这 15 个控制是标准 UVC 没定义的厂商私有控制——通常是曝光模式、增益、白平衡、降噪、图像翻转等厂商标定参数。

注意 bmControls = FF 03 00 00 只置位了低 10 位，即实际启用 control 1~10，其余 5 个未启用。

应用怎么用它们：向 VC 接口（接口 0）发 UVC 类请求 SET_CUR/GET_CUR：wValue 高位 = 控制号（1~10），低位 = Unit ID（10），wIndex = 接口号。含义只有厂商知道（对应海康 SDK 的私有控制项），第三方只能枚举 GET_INFO 试探可用性。这解释了 Q7——标准控制全关，私有控制是主通道。

Q7: 设备1&2 的 bmControls 全是 0，怎么控制摄像头？

对照 dump：

  • Camera IT 的 bmControls = 00 00 00 → 标准摄像头控制（曝光、增益、对焦等）全部未实现；
  • PU 的 bmControls = 00 00 → 标准处理控制（亮度、对比度等）全部未实现。

意味着对这些标准控制发 GET_CUR/SET_CUR，设备会回 STALL 或错误——它们真的不存在。实际控制通道是：

  1. XU 的 vendor-specific 控制（见 Q6）：10 个已启用的私有控制承担了真实的图像调节，需用厂商 SDK 访问；
  2. VS 接口的流控制：切格式、启停流走 VS 的 PROBE/COMMIT 类请求（VideoStreaming Interface Control），与 bmControls 无关；
  3. 其余参数（如自动曝光）由固件自动管理，不开放。

结论：bmControls=0 只代表"标准控制没实现"，不代表设备不可控——看 XU 和 VS 控制才是这类摄像头应用的正确姿势。做应用时先枚举 XU（GET_INFO），别假设标准控制可用。
