# Lesson 01 · 文档切分：RAG 的第一道杠杆

> 阶段 1 / Wave 1。代码：`src/rag/splitter.py`｜测试：`tests/test_splitter.py`｜对比脚本：`scripts/compare_splitter.py`

## 一、做什么 / 为什么 / 不做会怎样

**做什么**：把一篇长文档切成一块块小文本（chunk），供后续向量化与检索。

**为什么**：向量检索算的是「一段文本 ↔ 一个问题的语义相似度」。数据的最小单位就是 chunk：
- **块太大**：一块里混了好几个主题，检索命中了，但答案淹没在无关内容里 → 大模型抓不住重点、token 还贵
- **块太小**：语义被切碎（比如把「七天无理由退货」切成「七天」「无理由」），检索反而找不到
- **不做切分**（整篇当一块）：一篇 3000 字的文档只对应一个向量，等于「用一句话概括全文」——检索精度必然差

**一句话**：切分粒度是 RAG 调优的**第一个旋钮**，它错了后面 rerank/生成再强也救不回来。

## 二、三种策略（本模块都实现了，便于对比）

| 策略 | 怎么切 | 优点 | 缺点 |
|------|--------|------|------|
| `fixed` | 按固定字符数硬切，可设重叠 | 简单、块长整齐、可控 | 会切断句子/段落，破坏语义 |
| `recursive` | 按分隔符优先级（段落→换行→句号→空格）尽量在语义边界切 | 语义较完整、长度有弹性 | 逻辑稍复杂 |
| `markdown` | 按 `## ` 二级标题切，每节一块 | 最贴合技术文档结构，块≈一个主题 | 依赖文档有规范标题；无标题则退化 |

**重叠（overlap）** 的作用：让相邻块共享一段文本，避免「答案正好卡在两块的交界处、两边都不完整」。`fixed` 策略里用，牺牲存储换召回。

## 三、实跑数据（33 篇技术文档，单次实跑、未挑选）

```
策略               总块数      平均块长       最长块
fixed            472       484       500
recursive        570       361       500
markdown         621       314       500
```

**怎么读这组数**（这里有个值得记住的教训）：我最初**预设**「fixed 按规整窗口切，块数应该最多」——数据打脸了：fixed 块数**最少**（472）。原因：fixed 不理会文本结构，长文档里很多字符落在同一块；而 markdown 遇到 `##` 就切，技术文档标题密集 → 块最碎（621 块、平均仅 314 字）。

**教训**：调 RAG 时不要凭直觉断言哪个策略"应该"更好——**实跑数据说话**。这也是本 Wave 用对比脚本而非口头结论的原因。

## 四、TDD 是怎么走的（本 Wave 的实际过程）

1. **先写测试**（`tests/test_splitter.py`，6 条断言锁定期望行为）

## 五、三问法精读指引

1. **`_rec_split` 递归函数吃什么吐什么？**（答：吃「一段可能超长的文本 + 分隔符列表 + 上限 size」，吐「若干不超过 size 的片段」；超长片段用下一级分隔符再切，直到 `""` 兜底硬切）
2. **`markdown` 策略为什么要 `re.split(r"(?=^## )", ...)` 用前瞻？**（答：前瞻分割让 `## ` 留在每段**开头**而非被吃掉——这样每块都带标题，检索时标题也是语义信号）
3. **不写 `overlap` 会怎样？**（答：答案若横跨两块边界，两块都只含半句，检索命中但内容不完整——overlap 用冗余换边界完整性）
