① 文档切分：RAG 的第一道杠杆

阶段 1 / Wave 1 代码 src\rag\splitter.py 测试 tests\test_splitter.py 脚本 scripts\compare_splitter.py

做什么 / 为什么 / 不做会怎样

做什么

把一篇长文档切成一块块小文本（chunk），供后续向量化与检索。

为什么

向量检索算的是「一段文本 ↔ 一个问题」的语义相似度，而数据的最小单位就是 chunk：块太大——一块里混了好几个主题，命中了但答案淹没在无关内容里，模型抓不住重点、token 还贵；块太小——语义被切碎（把「七天无理由退货」切成「七天」「无理由」），检索反而找不到。

不做会怎样

整篇当一块：一篇 3000 字文档只对应一个向量，等于「用一句话概括全文」——检索精度必然差。

💡 一句话

切分粒度是 RAG 调优的第一个旋钮——它错了，后面 rerank / 生成再强也救不回来。

三种策略

策略怎么切优点缺点
fixed按固定字符数硬切，可设重叠简单、块长整齐、可控会切断句子 / 段落，破坏语义
recursive按分隔符优先级（段落→换行→句号→空格）尽量在语义边界切语义较完整、长度有弹性逻辑稍复杂
markdown按 ##  二级标题切，每节一块最贴合技术文档结构，块 ≈ 一个主题依赖文档有规范标题；无标题则退化

重叠（overlap） 的作用：让相邻块共享一段文本，避免「答案正好卡在两块的交界处、两边都不完整」。fixed 策略里用，牺牲存储换召回。

⚠️ 一个值得记住的教训

我最初预设「fixed 按规整窗口切，块数应该最多」——数据打脸了：fixed 块数最少（472）。原因：fixed 不理文本结构，长文档里很多字符落在同一块；而 markdown 遇到 ## 就切，技术文档标题密集 → 块最碎（621 块）。调 RAG 时不要凭直觉断言哪个策略「应该」更好——实跑数据说话。

三问法精读

_rec_split 递归函数吃什么、吐什么？
吃「一段可能超长的文本 + 分隔符列表 + 上限 size」，吐「若干不超过 size 的片段」；超长片段用下一级分隔符再切，直到 "" 兜底硬切。
markdown 策略为什么要用前瞻 (?=^## ) 分割？
前瞻分割让 ##  留在每段开头而非被吃掉——这样每块都带标题，检索时标题也是语义信号。
不写 overlap 会怎样？
答案若横跨两块边界，两块都只含半句，检索命中但内容不完整——overlap 用冗余换边界完整性。

② 向量检索：把文本变成能「算相似度」的东西

阶段 1 / Wave 2 代码 src\rag\embedder.py · store.py 测试 tests\test_embedder.py · test_store.py Demo scripts\demo_retrieve.py

做什么 / 为什么 / 不做会怎样

做什么

把课①切出的文本块向量化（embedding）存进向量库；查询时把问题也向量化，找「语义最近」的块。

为什么

关键词匹配做不到「语义相关但用词不同」。比如问「怎么防止模型编造订单号」，文档里写的是「防幻觉纵深：验证节点」——没有一个字相同，但语义相关。向量检索能命中，关键词检索不能。

不做会怎样

退化成关键词搜索，用户换个说法就搜不到——这正是 RAG 要解决的核心痛点之一。

embedding 内部就三步（没有魔法）

原文text
→
WordPiece 分词中文逐字 / 英文子词
→
ONNX 前向推理BGE-small-zh
→
池化 + 归一化取 [CLS]，除模长
→
向量可直接算相似度
💡 归一化的意义

归一化后，两个向量的点积 == 余弦相似度——检索时排序只需点积，省一次除法。这正是「为什么归一化后点积等于余弦」的直觉来源。

为什么用本地 ONNX 而不是 API：DeepSeek 没有 embedding API；chromadb 内置模型的 S3 下载国内不通。旧项目已下载好 BGE 中文模型，本模块复用它——这就是「不重新发明轮子」。

向量库：chromadb 的封装要点

🔌 embeddings 外部算好显式传入

不让 chromadb 用自己的 embedding function——否则它会去下载内置模型（国内会卡）。副作用是 store 能用假嵌入器独立测试（tests\test_store.py 用了 FakeEmbedder，又快又稳）。

📐 相似度用余弦，距离换算成相似度

建库用 metadata={"hnsw:space":"cosine"}；chroma 返回的是距离，本模块换算成 score = 1 - distance（越大越相似，符合直觉）。

三问法精读

为什么归一化后「点积 = 余弦」？
余弦 = 点积 /（模长乘积）；归一化让两个模长都 = 1，分母变 1，点积即余弦。
VectorStore 为什么不自己算 embedding、而要外部传入？
① 不让 chromadb 下载内置模型；② 解耦——store 可用假嵌入器独立测试；③ embedder 可替换而不改 store。
chroma 返回的 distance 和我们的 score 什么关系？
cosine 空间下 distance = 1 - 余弦相似度，故 score = 1 - distance；换算后语义是「越大越相似」。

③ 混合检索与精排：召回与排序是两件事

阶段 1 / Wave 3 代码 src\rag\bm25.py · retriever.py · reranker.py 测试 tests\test_bm25.py · test_retriever.py 对比 scripts\compare_retrieval.py

为什么需要「混合」：向量和 BM25 是互补的两个瞎子

强在弱在
向量检索语义相近（换词也能命中）专有名词 / 编号 / 精确术语在语义空间不突出，易漏
BM25关键词精确命中（术语、函数名、订单号）换个说法就搜不到

用户在找 create_agent 时，向量可能给你一堆「讲 agent 是什么」的泛泛段落；BM25 则死死盯住 create_agent 这个词。两者融合 = 混合检索，是生产级 RAG 的标配。

融合为什么用 RRF 而不是「分数相加」

向量相似度 ∈ [0, 1]，BM25 分数可达几十上百——尺度不同，直接相加没意义（BM25 会主导排序）。

🎯 RRF（Reciprocal Rank Fusion）只看排名

每个结果列表里，第 rank 名给该文档贡献 1/(k + rank)，多路结果求和。排名越靠前贡献越大，k（默认 60）起平滑作用。

向量榜（第 1、2 名）

docA → 1/(60+1) · docB → 1/(60+2)

BM25 榜（第 1、2 名）

docB → 1/(60+1) · docC → 1/(60+2)

↓ 两路求和 → 融合榜

docB = 1/62 + 1/61（两榜都靠前）胜出；docA、docC 各只在一路出现，排名靠后。共识项优先——这正是 RRF 的直觉。

💡 好处

RRF 免调参、对异构源更稳——它把任意尺度的分数都归一成「排名贡献」，不用去纠结「向量分和 BM25 分该配什么权重」。

精排（rerank）：召回之后再筛一遍

召回 ≠ 排序。混合检索先「召回」一批候选（如 20 个），但它们的顺序未必准。精排模型（cross-encoder）把「查询 + 候选」拼在一起喂模型打分，比向量距离准得多——代价是慢，所以只对少量候选做。

⚠️ 本项目的诚实降级

真正的 cross-encoder（如 BGE-reranker）需要额外下载模型（国内可能受阻，本项目未验证可获取性）→ 采用降级实现：用「查询词在候选中的覆盖率」重排。下面的数据会显示这个降级版并不总优于 RRF——这正是「没有真精排模型就别吹精排」的实证。

🔍 怎么读（诚实分析）

2. 降级 rerank 不稳定：最后一例里，覆盖率重排反而把正确的 eval 文档挤掉、换成了 agent1。结论：没有真正的 cross-encoder 模型时，别迷信「加了 rerank 就更好」。

TDD 过程与踩坑

展开：BM25 的一个反直觉行为

先用 BM25Okapi，测试挂了——两个小测试失败（一个 IndexError、一个排序错）。根因：BM25Okapi 的 IDF 公式在小语料上会失真——词恰好出现在一半文档时，IDF = log((N-n+0.5)/(n+0.5)) = log(1) = 0，导致正确块得 0 分被过滤。改用 BM25Plus（IDF 恒非负）解决。

教训：经典算法在小数据上有边界行为，测试小语料反而更容易暴露它。RRF 的 3 条测试（共识项优先 / 单路保序 / 分数正且降序）也是先红后绿。

三问法精读

RRF 为什么能容忍两路分数尺度不同？
它只用 rank 不看 score，1/(k+rank) 把任意尺度的分数都归一成「排名贡献」。
为什么不干脆把向量和 BM25 分数加权相加？
尺度不可比，权重极难调；RRF 免调参、对异构源更稳。
Reranker(mode="coverage") 和真 cross-encoder 差在哪？
coverage 只看词是否出现，不懂语义；cross-encoder 把 query+doc 一起过模型，理解语义相关度，但需模型且慢。

④ 检索评估与服务化：让「好不好」变成数字

阶段 1 / Wave 4 代码 src\evaluation\evaluate.py · src\api\main.py · src\rag\generator.py 脚本 scripts\run_eval.py · scripts\ask.py

为什么必须评估：调优不能靠感觉

前三课做了切分 / 向量 / 混合 / 精排——但「哪个策略更好」不能凭嘴说。评估把「感觉准」变成可计算的三个指标：

指标问的问题怎么算
hit_rateTop-K 里有没有命中相关文档？有命中的问题数 / 总问题数
recall@k相关文档被找全了吗？（一条问题可有多篇相关文档）Top-K 覆盖的相关文档比例，取平均
MRR正确的排得靠前吗？第一个相关文档排名的倒数（第 1 名=1，第 2 名=0.5…），取平均

指标全用可编程判据（子串 / 集合运算），不靠第二个 LLM 评判——透明、可复现、零成本。

三问法精读

create_app(retriever, generator) 为什么要能注入？
测试用假件隔离 HTTP 层、零成本；生产用真件；同一份路由代码两种场景复用——这就是依赖注入对可测试性的价值。
为什么 run_eval 的指标用集合运算而不是让 LLM 打分？
透明、可复现、零成本、不引入第二个模型的随机性；LLM 评判会引入裁判自身的偏差。
降级 rerank 的 MRR 为什么暴跌？
coverage 只看「查询词是否出现」，不理解语义重排——它把 RRF 已排好的顺序打乱，把词面偶然匹配但语义不相关的块提前了。
