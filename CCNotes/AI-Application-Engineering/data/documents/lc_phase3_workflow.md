# Phase 3：构建协议生成工作流

> 对应脚本：`scripts/phase3_1_doc_input.py`、`scripts/phase3_2_prompt_chain.py`
> 目标：从"命令行一句话"升级为"喂一个文件，输出完整协议规范"。

---

## 3.1 文档输入：三个实际问题

| 问题 | 现实场景 | 对策 |
|------|---------|------|
| **编码** | 中文文档 UTF-8 / GBK 混杂 | 按 `utf-8-sig → utf-8 → gb18030` 顺序尝试解码；gb18030 是 GBK 超集，中文全覆盖，无需第三方库 |
| **大小** | 上下文窗口有限（DeepSeek-chat 64K token） | 估算 token（中文 1 字符 ≈ 1 token），超限警告；RAG（Phase 4）才是治本方案 |
| **噪声** | 需求文档含背景、硬件选型、无关信息 | 全文直塞给 LLM 提取——从噪声中提关键信息是模型强项，不要自己写解析规则 |

**核心原则：先跑通"全文直塞"，不提前优化。** 实测：503 字符带噪声的文档直塞，模型正确过滤噪声并提取 7 个字段，还自发做了协议设计推理（int16×0.1 存温度、加 message_type、预留扩展字节）。

## 3.2 Prompt 模板链：一段式 → 四步链

**一段式的三个问题**：丢步骤（要求多容易漏）、中间过程不可见（错了不知道哪步）、无法单步调参（分析要发散、定义要严谨，只能折中）。

**链设计**（每步职责单一）：

```
需求文档
  │
  ▼ ① 需求分析   Prompt → StrOutputParser   关键需求点（纯文本）
  │
  ▼ ② 字段定义   Prompt → JsonOutputParser  字段表（JSON）
  │
  ▼ ③ 约束规则   Prompt → JsonOutputParser  范围/边界/异常/扩展 + 评审 issues
  │
  ▼ ④ 最终协议   纯 Python 合并（不是 LLM！）
```

**三个关键决策**：

1. **`.assign()` 挂键**：`RunnablePassthrough.assign(key_points=分析链)` 每步往数据流挂一个键，下游自动可见。**挂的键名必须与下游 Prompt 占位符一致**——不一致当场报错，这是防漏配的保护机制（实操中撞过一次：键 `protocol` vs 占位符 `{fields}`）。
2. **④ 用 Python 不用 LLM**：合并是确定性操作。原则：**LLM 做推理，Python 做拼装**。省一次调用，且模型不会在合并时改写/丢字段。
3. **中间产物必须可见**：实操中 ③ 评审环节发现了 3 条一段式永远发现不了的 warning（如"预留扩展位 1 字节可能不够装光照数据"）。评审视角与生成视角分离，是链式最大的价值。

## 3.4 验收：单一入口 + 数据/呈现分离

最终交付物：`scripts/generate_protocol.py` —— 文件路径进 → 协议规范出。

| 输出 | 用途 |
|------|------|
| `<名称>_protocol.json` | 机器可读的结构化协议（程序用） |
| `<名称>_protocol.md` | 人可读的协议规范文档（同事看），纯 Python 渲染 |

设计要点：**JSON 是"数据"，Markdown 是"呈现"，两者分离。** LLM 只负责推理出 JSON；渲染成文档是确定性工作，用 Python 做（样式可改、无随机性）——"LLM 做推理，Python 做拼装"在输出端同样成立。

验收结果：2 份文档跑通；智能水表协议产出 10 字段、5 条约束、7 条评审发现（含"量程清零后新旧数据混淆"这类真实设计风险，评审环节的价值再次验证）。
