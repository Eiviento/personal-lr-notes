# Phase 1：Prompt Engineering 基本功

> 对应脚本：`scripts/phase1_4_req_to_protocol.py`（纯 SDK 实操）
> 目标：不用任何框架，先学会把话说清楚，让模型稳定输出你要的格式。

---

## 1.1 Prompt 四要素

| 要素 | 作用 | 示例 |
|------|------|------|
| **角色** | 定位模型的行为边界和知识域 | "你是一位资深的通信协议工程师" |
| **指令** | 要做什么，动词开头、具体 | "分析需求，提取所有需要通信的数据字段" |
| **上下文** | 背景材料，越具体模型越少瞎编 | 需求文档全文、格式要求、领域约束 |
| **输出格式** | 给模板，让模型照着填 | 完整的 JSON 骨架 + 字段说明 |

**为什么有效**：模型是在"补全"——你给的结构越完整，它补的内容越可控。角色不是玄学，它激活了模型参数里对应领域的知识分布（协议术语、类型选型习惯）。

## 1.2 Few-shot Prompting

给 1~3 个"输入 → 期望输出"的例子，让模型模仿风格和格式。

**原理**：模型本质是模仿引擎。描述十遍"字段名用英文驼峰"，不如一个例子直接。Few-shot 对格式一致性提升最大，对领域知识提升有限。

**坑**：示例必须来自真实协议。教学用的假例（心跳包/固件升级）在正式模板里必须替换成用户自己的真实协议，否则模型会学走假例的字段风格。

## 1.3 结构化输出三法

| 方法 | 做法 | 可靠性 | 代价 | 适用 |
|------|------|--------|------|------|
| **Prompt 约束** | 在 Prompt 里写死 JSON 格式要求 | 中（偶有围栏/废话） | 无 | Phase 1-3 现阶段 |
| **JSON Mode** | API 参数强制 JSON | 高 | 需 API 支持 | 后续可选 |
| **Tool Calling** | 用函数签名声明 schema | 最高 | 实现复杂 | Phase 4 再上 |

**为什么阶段 1-3 用 Prompt 约束**：先理解"模型输出本来不稳定"这件事本身，再上工具；直接上 Tool Calling 会跳过后面的故障排查能力。

**容错手段（1.4 实操落地）**：手写解析器处理三类情况——markdown 代码块围栏（` ```json `）、前后多余文字、`json.loads` 失败时用第一个 `{` 到最后一个 `}` 截取。
