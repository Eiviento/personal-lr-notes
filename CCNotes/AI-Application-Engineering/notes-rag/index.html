① 向量化：把文本变成箭头

代码 src\rag\embedder.py 实验 examples\e1_vector_basics.py 实验 examples\e2_embedding_real.py

直觉：每个文本是一根箭头

向量化要解决的问题是：怎么让计算机知道「两句话意思差不多」？

办法是给每个文本造一个「坐标」——但更准确的比喻是一根从原点射出去的箭头。模型被训练成：意思相近的文本，箭头指向相近的方向。于是「像不像」这个模糊的问题，变成了「两根箭头夹角大不大」这个能算的问题。

💡 为什么是「方向」不是「距离」

一句话写长一点、短一点，箭头会变长变短，但方向不变——意思没变。所以衡量相似度要看去向（夹角），而不是长度（距离）。这就是「余弦相似度」的由来。

三步机制（把 embedder.py 拆开）

embedder.py 里的 _embed_one() 其实只做了三件事，没有魔法：

1 分词WordPiece
→
2 前向推理ONNX / BGE
→
3 池化 + 归一化取 [CLS]
→
一根单位箭头512 维
步做什么为什么
1 分词把文本切成 token，再查词表换成数字 id（中文基本逐字切，英文按子词）模型只认数字，不认字
2 前向推理把 id 序列喂进神经网络，每个位置吐出一个向量这是「懂语义」的地方——权重是从海量语料学来的
3 池化 + 归一化取 [CLS] 位置那个向量当整句代表，再除以自己的模长归一化让箭头长度变成 1——于是点积就等于余弦，排序省一次除法

对应代码：src\rag\embedder.py 的 WordPieceTokenizer.encode() / _embed_one()

余弦相似度：夹角的余弦

两个向量 a、b 的余弦相似度：

cos(a, b) = (a · b) / (|a| × |b|) = 点积 / (a 的长度 × b 的长度)
cos 值两根箭头的关系含义
1完全同向意思基本一样
0垂直毫不相关
−1完全反向意思相反（实际文本里很少见）
✅ 关键性质

归一化之后 |a| = |b| = 1，公式的分母变成 1——于是 点积 == 余弦相似度。这就是 embedder.py 最后一步归一化、以及检索时直接用点积排序的原因。

看完整的相似度矩阵（同一份输出）：

② 检索：两条完全不同的路

代码 src\rag\store.py · src\rag\bm25.py 实验 examples\e3_retrieval.py

两条完全不同的路

「检索」听起来是一个动作，其实项目里跑了两套完全不同的算法，它们的思路毫无共同点：

向量路BM25 路
怎么算把 query 也编码成箭头，和每个块的箭头算余弦统计「query 里的词在这个块里出现了几次」
看什么语义 —— 懂「换词同义」字面 —— 只认字符本身
强在换种说法也能找到专有名词 / 编号 / 函数名（SO-1003、create_agent）
弱在精确术语在语义空间不突出，容易漏换个说法就彻底找不到
本项目代码store.query() → 余弦排序BM25Index.query() → 打分排序

两个「瞎子」互相补位——这正是下一节要「融合」的原因。

BM25 在算什么

BM25 的思路一句话：一个块要得高分，得让 query 里的词既在本块里常见、又在整个语料里罕见。

TF —— 词频

这个词在这个块里出现了几次。

出现越多，说明这个块越可能在讲它。但不会无限加分（出现 100 次不等于相关 100 倍），所以做了饱和处理。

IDF —— 逆文档频率

这个词在整个语料里有多稀有。

「的」「是」到处都是 → 区分度为零；SO-1003 只在一处出现 → 区分度极高。

每个块的 BM25 分 = Σ 对 query 里的每个词： TF(词, 块) × IDF(词) ← 再加一点常数项（BM25Plus 的稳定性设计）
💡 一句话记住

向量路比的是「意思像不像」，BM25 比的是「词重不重合」。前者靠模型学出来的本领，后者靠数数——所以 BM25 完全不懂「同义词」，但也因此绝不会因为「语义相似」而放过一个精确编号。

  → 两路都命中：['3. 订单系统']
  → 只有向量命中：['4. Agent 工具', '6. 用户偏好']
  → 只有 BM25 命中：['1. 设备定位', '2. 天气查询']

问：怎么知道设备的位置                     # 语义提问

这张表要看什么

  1. 两路的 Top-1 常常一致，但 Top-2/3 就分岔了——「SO-1003」那题，向量把「用户偏好」「Agent 工具」拉进来，BM25 却在「设备定位」「天气查询」上给了分。两路各有各的「只有它命中」的块。
  2. 分数尺度差了近一个数量级：向量是 0.5356，BM25 是 4.002（另一题甚至到 22.234）。这正是下一节「不能直接相加」的实锤。
  3. BM25 的分数是「无上界」的——它不像余弦被压在 [0,1] 里。分数多大取决于语料和查询，跨查询比较没意义。
⚠️ 注意本项目 BM25 的分词方式

它用的是「中文单字」轻量分词（见 bm25.py 的 tokenize()）——所以「设」「备」这样的常用字会到处撞上，容易产生明显不相关却也拿到分的块（比如「SO-1003」那题里「设备定位」拿到 1.946）。

这是教学级实现，生产环境会换 jieba 等更细的分词（代码注释里也写了「够用；生产可换」）。但两路「各有所长、结果不重合」的大格局不变——所以融合依然必要。

✅ 结论

没有任何一路能单独覆盖所有情况。向量漏术语，BM25 漏语义——把它们的结果合起来，才可能取长补短。这就是「混合检索」，也是下一节的全部动机。

③ 融合：把两路合成一路

代码 src\rag\retriever.py 的 reciprocal_rank_fusion 实验 examples\e4_fusion_rrf.py

为什么不能直接相加

拿到两路结果后，最直觉的做法是「分数加起来排序」。但上一节的实测已经说明它行不通：

文档（SO-1003 那题）向量分BM25 分直接相加
3. 订单系统0.53564.0024.5371
2. 天气查询0.28161.9462.2276
1. 设备定位0.26231.9462.2082

以上是 e3_retrieval.py 里「如果直接相加」那段的真实输出（脚本会顺带算出来，你重跑就能看到）。

注意被挤掉的是谁：「用户偏好」在向量路里排第 2（0.4028），相加后却掉出了前三——因为 BM25 没提到它，它的 BM25 分是 0，总分就只有 0.4028。

反过来，「天气查询」「设备定位」在向量路里连前三都没进（只有 0.28 / 0.26，基本无关），却靠着 BM25 的 1.946「底分」被抬到了第 2、3 名。

这就是「BM25 主导」的实证：加法的结果几乎只由 BM25 的分数决定，向量那路辛苦算出的语义判断，被数值直接淹没了。

那么换成 RRF 呢？同一个问题（SO-1003），同一个脚本还输出了第三种答案：

e3 输出 · RRF 融合（同一题）
【RRF 融合】只看排名，1/(60+rank) 求和（← 项目真实做法）
    #1  rrf=0.032787   3. 订单系统
    #2  rrf=0.031498   4. Agent 工具
    #3  rrf=0.031281   6. 用户偏好

把三种方式并排看（都是同一题、前 3 名）：

融合方式#1#2#3
只用向量路订单系统用户偏好Agent 工具
直接相加订单系统天气查询设备定位
RRF（项目做法）订单系统Agent 工具用户偏好

看出差别了吗：RRF 的 #2/#3 与「只用向量路」完全一致（Agent 工具、用户偏好），只是顺序按两路共识做了微调；而「直接相加」把向量路认为**根本无关**的「天气查询」「设备定位」顶了上来。

✅ 这就是 RRF 赢在哪

向量路给出的语义判断（订单系统最相关，其次是 Agent 工具、用户偏好），RRF 保住了；而直接相加让它被 BM25 的分数噪声淹没。

原因回到 RRF 的设计：它只看排名，所以向量榜的「第 2、第 3 名」和 BM25 榜的「第 2、第 3 名」被平等对待——不会因为某个分数数值大，就把另一路的判断整个盖掉。

✗ 问题在哪

两路的分数根本不在一个尺度上：向量的余弦被压在 [0, 1] 区间，而 BM25 的分数可以到几十几百。

把它们相加，等于让 BM25 一个人说了算——向量那路辛苦算出来的语义信息，在数值上被彻底淹没。而且 BM25 的分还会随语料规模变化，你甚至没法调一个「固定的权重」来救它。

RRF：干脆扔掉分数，只看排名

既然分数不可比，那就不要分数——只保留「谁排第几」这个信息。这就是 RRF（Reciprocal Rank Fusion，倒数排名融合）：

对每一路结果：第 rank 名的文档，贡献 1 / (k + rank) （k 通常取 60） 把所有路的贡献加起来 = 这个文档的最终 RRF 分

为什么这样就公平了？因为排名是两路唯一的共同语言。向量说「A 排第 1」，BM25 说「C 排第 1」——两句话都可以翻译成「贡献 1/61」，尺度问题自然消失。

💡 RRF 的核心直觉：共识项胜出

一个文档如果在两路里都排得靠前，它就能拿到两份贡献，自然超过只在单路里排第一的文档。换句话说：「两边都觉得你不错」比「一边觉得你最好」更可信。

k 是什么，为什么是 60

公式里的 k 是个平滑旋钮：它决定「排名差异」被放大还是被抹平。

e4 输出 · k 的作用（节选）

k=1000  前三： A=0.0020  C=0.0020  B=0.0020

自测：能答上来就说明懂了

为什么 embedder.py 最后一定要归一化？
归一化后两个向量的模长都是 1，余弦公式的分母变成 1——于是点积就等于余弦，检索排序时可以省掉一次除法，直接用点积。
为什么 BM25 完全找不到「换词同义」？
因为 BM25 的输入是词本身：它统计的是「query 里的这些字符，在块里出现了几次」。既然字都不一样，TF 就是 0，它没有任何办法知道两个词意思一样——那是模型的本领，不是数数的本领。
RRF 为什么不看分数、只看排名？
因为向量分（0~1）和 BM25 分（可达几十上百）尺度不可比，相加等于让 BM25 主导。而「排名」是两路唯一的共同语言——把「第 rank 名」换算成 1/(k+rank)，两路就站到了同一个尺度上。
在 e4 里，C 是 BM25 榜第 1，为什么总分输给了 A？
因为 A 在两路里都靠前（向量 #1 + BM25 #2 = 1/61 + 1/62），而 C 只在 BM25 里第 1、向量里掉到第 3（1/61 + 1/63）。RRF 奖励的是共识，不是单路的冠军。
为什么真实模型的相似度「都挤在一起」？
e2 的矩阵里，0 vs 1（语义相关）是 0.446，而 0 vs 3（不相关）是 0.436——只差 0.01。真实 embedding 的相似度分布是连续且拥挤的，绝对值很难直接当阈值用。所以系统里靠的是排序，不是分数——这也是 RRF 敢扔掉分数的底气。
✅ 一句话总收

向量化把文本变成箭头，让「语义像不像」变成能算的夹角；检索用两条互补的路（懂语义的向量 + 认字面的 BM25）各自找候选；融合因为分数不可比，改用排名来做公平的合并。
