# 认证与会话机制笔记

> 核心问题只有一个：**服务器怎么确认"这次请求是登录过的某某发的"？**
> 三种方案的差别在于——"凭证放在哪、算什么、服务器要不要记账"。

---

## 0. 总览：一条主线

```
浏览器/客户端  ──请求──▶  服务器
        ▲                    │
        └──── 凭证 ──────────┘

问题：凭证长什么样？放在哪？服务器要不要存东西？
```

| 概念 | 本质 | 一句话 |
|---|---|---|
| **摘要认证 (Digest)** | HTTP 协议原生 scheme | 密码不上网，传的是"密码参与算出的指纹" |
| **Session 认证** | 应用自己搭的会话层 | 服务器记账，给客户端一个"座位号" |
| **Token** | 一类凭证的统称 | 可能是随机串，也可能是 JWT |
| **JWT** | Token 的一种格式 | 信息自包含 + 签名防篡改 |

关键认知：**Session vs Token 是两个维度**（状态放哪），**JWT 是 Token 的一种格式**。不是三个并列方案。

## 1. 摘要认证（HTTP Digest Authentication）

### 1.1 先看 Basic 认证有多糟

```
GET /admin HTTP/1.1
Authorization: Basic YWxpY2U6c2VjcmV0
```

`YQ==` 这种是 **Base64 编码，不是加密**。解开就是 `alice:secret`——抓包即得明文密码。所以 Basic **必须配 HTTPS**。

### 1.2 Digest 的做法：密码不上网

第一步，客户端请求（无凭据）：

```
GET /admin HTTP/1.1
Host: example.com
```

第二步，服务器回"挑战"：

```
HTTP/1.1 401 Unauthorized
WWW-Authenticate: Digest realm="example.com",
                  qop="auth",
                  nonce="dcd98b7102dd2f0e8b11d0f600bfb0c093"
```

`nonce` = 服务器每次随机给的数，防重放。

第三步，客户端用密码算出摘要，重发：

```
GET /admin HTTP/1.1
Authorization: Digest username="alice",
                    realm="example.com",
                    nonce="dcd98b7102dd2f0e8b11d0f600bfb0c093",
                    uri="/admin",
                    qop=auth, nc=00000001, cnonce="0a4f113b",
                    response="6629fae49393a05397450978507c4ef1"
```

摘要公式（qop=auth 时）：

```
HA1 = H(username : realm : password)     # 密码在这里，算完不外传
HA2 = H(method : uri)
response = H(HA1 : nonce : nc : cnonce : qop : HA2)
```

`H` 早期是 MD5（RFC 2617），新版支持 SHA-256（RFC 7616）。服务器存有密码，用同公式重算，一致即放行。

> **RFC 2617 经典示例**：用户名 `Mufasa`、realm `testrealm@host.com`、密码 `Circle Of Life` → `response=6629fae4...`

### 1.3 关键区别

- Basic：传**密码本身**
- Digest：传**密码参与算出的指纹** → 网线上没有明文密码，且 nonce 防重放

### 1.4 为什么今天基本见不到

- 依赖弱算法 MD5；换 SHA-256 又要求服务端**存明文密码**（realm 要参与计算）——很别扭
- 实现复杂：nonce 池、`nc` 计数器、多 qop 分支
- **不能注销**：无状态一次性校验，没法作废"已认证状态"
- 前端不友好：浏览器/`fetch` 不会自动算摘要，前后端分离场景用不了

**结论**：HTTPS 普及后，Basic 的明文风险被信道加密消除，Digest 的复杂度失去意义。主流 = HTTPS + Session/JWT。

## 2. Session 认证：服务器记账，你拿座位号

### 2.1 思路

**不在凭证里藏信息，而是服务器自己记一本账。**

### 2.2 流程实例

第 1 步，登录：

```
POST /login
{ "username": "alice", "password": "secret" }
```

验证通过后，生成随机 `sessionId`，**存到服务端**（内存 / Redis / 数据库）：

```
Redis:  sess:abc123xyz  ->  { userId: 42, name: "alice", loginAt: 1700000000 }
```

通过 Cookie 发座位号：

```
HTTP/1.1 200 OK
Set-Cookie: SESSIONID=abc123xyz; HttpOnly; Secure; SameSite=Lax; Path=/
```

第 2 步，后续请求浏览器**自动**带上：

```
GET /orders
Cookie: SESSIONID=abc123xyz
```

服务器查 `abc123xyz` → 查到 `{ userId: 42 }` → 知道是 alice。

服务端代码（Express 风格）：

```js
app.post('/login', (req, res) => {
  const user = verify(req.body.username, req.body.password);
  if (!user) return res.status(401).end();
  req.session.userId = user.id;   // 写进服务端 session 存储
  res.json({ ok: true });          // Set-Cookie 由框架自动带上
});

app.get('/orders', (req, res) => {
  if (!req.session.userId) return res.status(401).end();  // 查账
  res.json(getOrders(req.session.userId));
});
```

### 2.3 两个特点

1. **座位号本身没有意义**：`abc123xyz` 只是随机数，不含用户信息。真正认识你的是服务器那本账。
   - 好处：**想让你下线，删掉 key 即可** → 这是最大优势——随时可踢人
2. **它是有状态的**：多机部署时，请求被负载均衡打到别的机器会"丢人"。
   - 解法：共享 session 存储（Redis），或粘性会话（sticky session）

## 3. Token / Session / JWT：理清使用场景

### 3.1 先破除混淆

- **Session vs Token**：比的是"**身份状态放在哪**"——服务器（Session）vs 客户端带着（Token）
- **JWT**：Token 的**一种具体格式**（自包含）；Token 也可以是不透明随机串

正确问法：**"用 Session 还是 Token？若用 Token，用不用 JWT 格式？"**

### 3.2 不透明 Token（Opaque Token）

```
POST /login  ->  { "access_token": "9f8c1e...", "expires_in": 3600 }

GET /orders
Authorization: Bearer 9f8c1e...
```

服务器查表 `9f8c1e... -> userId 42`。

**本质和 Session 一回事**（服务端仍记账），只是不用 Cookie、改用 `Authorization` 头。
- 好处：绕开 Cookie 跨域限制，一样能吊销 / 统计 / 限流
- 实例：GitHub PAT、微信/支付宝开放平台 `access_token`

### 3.3 JWT（JSON Web Token）

```
eyJhbGciOiJIUzI1NiJ9 . eyJzdWIiOiI0MiIsIm5hbWUiOiJhbGljZSIsImV4cCI6MTcwMDAwMDAwMH0 . 签名
     header                    payload                                       signature
```

三段点分，各自 Base64Url：

- header：`{"alg":"HS256","typ":"JWT"}`
- payload：`{"sub":"42","name":"alice","exp":1700000000}` ← **身份写在这**
- signature：用服务器密钥对前两段签名

验证时**不需查库**：

1. 用密钥重算签名，对上 → 内容没被改
2. 看 `exp` 没过期 → 放行
3. 从 payload 直接读出 `userId=42`

**这就是"无状态"**：服务器不存东西，token 自己就是证据。适合多机、微服务传递身份。

**代价**：

- **签出去收不回**（`exp` 到期前一直有效）→ 想踢人得额外维护黑名单 → 一旦维护就不无状态了
- 常见折中：**短过期 access token（如 15 分钟）+ 长效 refresh token**
- **payload 是明文（Base64 非加密）** → 谁都能解开看，绝不塞敏感信息
- 体积大，不便主动作废单个会话

### 3.4 场景对照

| | 状态存在哪 | 能即时踢人吗 | 典型场景 |
|---|---|---|---|
| **Session** | Cookie 存座位号，服务器存账 | 能（删账即可） | 传统服务端渲染网站、后台管理、单体应用 |
| **JWT** | 全在客户端，自包含 + 签名 | 不能（除非加黑名单） | 前后端分离 SPA + API、微服务间鉴权、移动 App、跨域 |
| **不透明 Token** | 客户端持有，服务器可查表 | 能 | 第三方 API 授权（OAuth2 access_token）、PAT、开放平台 |

### 3.5 怎么选（一句话版）

- 传统网站 / 要"登出立即生效" / 单体 → **Session**
- 前后端分离 / 微服务 / 跨域 / 移动端 / 服务端不记状态 → **JWT**（短效 access + refresh）
- 开放给第三方 / 要随时吊销 / 按 token 限流统计 → **不透明 Token**
- 想"无状态"又想"能踢人" → 天生冲突：回到不透明 Token，或 JWT + 黑名单 / 短过期

### 3.6 三个误区

- ❌ "JWT 比 Session 更安全" → 取决于实现（HTTPS、密钥、存储位置），不是格式
- ❌ "无状态一定更好" → 需要主动吊销会话时，无状态反而是负担
- ❌ "JWT 内容是加密的" → payload 只是 Base64，解一下就能读

## 4. 密码怎么处理：两个层面

Session 认证里登录请求：

```
POST /login
{ "username": "alice", "password": "secret" }
```

### 4.1 传输层 —— 靠 HTTPS

应用层报文里密码是原始值，**所有**认证方案都一样（服务器得拿到它才能验证）。
但 HTTPS 把整条请求加密后上线，抓包只得乱码。**线路上非明文。**

> 摘要认证的 hash 是**应用层**再算一层；HTTPS 是**传输层**整体加密。目标相同，Digest 诞生时 HTTPS 未普及，故只能自己在应用层想办法。

### 4.2 存储层 —— 必须加盐哈希

**绝不能把密码原样存库。**

```
注册：
  salt = 随机生成
  stored = bcrypt("secret", salt)
  存 { username, password_hash: stored, salt }

登录：
  输入 "secret" + 库中 salt 重算，与 password_hash 比对
```

- 为什么：库被拖（SQL 注入 / 备份泄露）时，明文=全泄露；哈希=一堆没法反推的串
- 盐（salt）：同密码的两个用户，库中值也不同 → 挡"彩虹表"
- 推荐：**bcrypt / scrypt / argon2**；不要 MD5/SHA1 裸哈希（太快，可暴力撞）

### 4.3 一个反直觉点

**Digest 反而强迫服务端存明文密码**（realm、username 要参与计算）。
而 Session 走"登录验证一次、之后靠 sessionId 认人"，服务端**不需要**明文，存 bcrypt 哈希即可。
→ **这一点上 Session 比 Digest 更安全。**

## 5. 踢人 / 吊销：token 在用户手里怎么办

**"踢人"不是把凭证抢回来，而是让服务器不再认它。** token 每次使用都要过服务器这关。

三种做法，代价递增：

### 5.1 短过期 + 可吊销的 refresh token（最主流）

access token 15 分钟过期，用 refresh token 换新的：

```
POST /token/refresh
{ "refresh_token": "rt_9f8c1e..." }
→ { "access_token": "at_(新的)", "expires_in": 900 }
```

refresh token **存在服务器数据库**（有状态）。踢人：

```sql
DELETE FROM refresh_tokens WHERE user_id = 42;
```

结果：现有 access token 最多再用 15 分钟；过期后换不到新的 → 彻底掉线。
**没法立即消失，但设了上限。**

### 5.2 Token 版本号（改密码 = 全端下线）

```
users: { id: 42, name: "alice", token_version: 3 }
JWT payload: { "sub": "42", "v": 3, "exp": ... }
```

改密码时：

```sql
UPDATE users SET token_version = 4 WHERE id = 42;
```

带 `v:3` 的旧 token 全被拒 → **改一次密码，所有设备同时失效**。
代价：每请求查一次 `token_version`（通常放 Redis）。

### 5.3 黑名单

```
Redis SETEX revoked:jti_abc123  900  "1"    # TTL = token 原剩余寿命
```

验签后再查是否在黑名单。封号时把 `jti` 扔进去，立即失效。
代价：要查、有状态，且需设 TTL 防膨胀。

### 5.4 本质权衡

- 彻底无状态 → 不能踢人，只能等 `exp`（纯 JWT 的天花板）
- 要能踢人 → 必须引入服务端状态（黑名单 / 版本号 / refresh），每请求多一次查询

### 5.5 对比 Session

Session 的账本本就在服务器，**删 Redis key 即可立即失效**，没有 15 分钟窗口。

> **一句话**：Session 把状态放服务器，JWT 塞给客户端；状态放哪，决定你能不能随时收回权力。

## 6. 有没有"基于 HTTP 的 Session 认证"

分两种理解，答案相反：

- **跑在 HTTP 之上** → **有，Session 认证就是**。`Set-Cookie`、`Cookie:` 都是标准 HTTP 头。
- **HTTP 标准原生定义了 Session 这类 scheme** → **没有**。RFC 9110 第 11 章注册的是 Basic / Digest / **Bearer**，没有 Session。

### 6.1 为什么后者不存在

**HTTP 本身是无状态的**（设计前提，不是缺陷）。它最细粒度是"一请求一响应，两不相干"。Session 要解决的恰是"跨请求记住你是谁"——属于在无状态协议上**人为补出的会话层**，只能应用自己建。

### 6.2 HTTP 原生 scheme（每请求带凭据、逐请求验证）

```
Authorization: Basic YWxpY2U6c2VjcmV0
Authorization: Digest username="alice", response="6629fae4..."
Authorization: Bearer eyJhbGciOi...
```

> `Bearer`（RFC 6750）只管"怎么把 token 放进请求头"，**不管 token 内容与校验**。塞 JWT 还是塞服务端可查的随机串都行。

### 6.3 "HTTP 上的 session 认证"实际形态

- **形态一：Cookie**（最主流）—— RFC 6265，独立标准
  ```
  Set-Cookie: SESSIONID=abc123xyz; HttpOnly
  Cookie: SESSIONID=abc123xyz
  ```
- **形态二：sessionId 塞进 Bearer** —— 即"不透明 Token"，只是从 Cookie 头挪到 Authorization 头
  ```
  Authorization: Bearer abc123xyz
  ```
- **形态三：自定义头** `X-Session-Id: ...`（不标准）

### 6.4 历史点

Cookie 不是 HTTP 一开始就有的——1994 年前后由 Netscape 先实现，后经 RFC 2109 → RFC 2965 → **RFC 6265** 标准化。**它是"被 HTTP 标准收编的扩展"。**

## 7. 防重放

### 7.1 结论先给

**Session 认证在应用层完全不防重放，防重放责任整个甩给 HTTPS。** 与 Digest 路线相反。

### 7.2 为什么应用层防不了

```
GET /orders
Cookie: SESSIONID=abc123xyz     # 每次请求重放同一个 sessionId
```

服务器无法区分"本人正常使用"和"攻击者截获后重发"——**两者在应用层完全相同**。
Digest 每请求用新 nonce 重算，能说"这 nonce 用过"；Session 要做到这点需为每会话维护计数器，且并发/乱序会炸 → 干脆下沉一层。

### 7.3 四种重放与堵法

**① 抓包重放（原样再发）** → HTTPS 基本堵死
TLS 记录层带**递增序列号**：
```
攻击者重发旧加密包 → 序列号=5，服务器已收过 → 丢弃
```
> HTTPS 不只"别人看不懂"，也"别人不能原样重发"。

**② cookie 泄露后重放（Session 劫持）** ← **真正的死穴，HTTPS 救不了**
攻击者拿到 `abc123xyz`，在自己机器上：
```
GET /orders
Cookie: SESSIONID=abc123xyz     # 合法 cookie，全新 TLS 连接
```
服务器看到的是**完全正常的请求** → 重放成立。
防御全靠"拿到"这一关：`HttpOnly`（防 JS 偷）、`Secure`（防明文截）、短过期/改密失效（缩窗口）、会话绑定（IP/UA，不可靠）。
**一旦 cookie 真被拿到，没有第二道防线。**

**③ CSRF（借你的浏览器重放）** → 攻击者不窃取 cookie，诱导你浏览器带 cookie 发请求
```html
<img src="https://bank.com/transfer?to=attacker&amount=10000">
```
防御：`SameSite=Lax/Strict`（跨站请求不带 cookie）。

**④ 应用层重放** → Session 无解（HTTPS 被降级或攻击者持解密能力时）。

### 7.4 抽象：bearer vs proof-of-possession

- `SESSIONID` 是 **bearer 凭证（持票即可）**——谁拿着都算数，不绑人、不绑机器
- Digest 的 `response` 每请求一变 → 更接近 **proof-of-possession（持有同时要证明会算）**
- **bearer 凭证的宿命：不能防重放，只能防泄露**

### 7.5 现代方向

**OAuth DPoP**（RFC 9449）：客户端用私钥对每个请求签名，服务器验签。
→ 攻击者截获 token 也没私钥，发不出合法请求 → 重放自然失效。是 bearer 模型的升级方向。

### 7.6 对比表

| | 摘要认证 | Session 认证 |
|---|---|---|
| 防重放的层 | 应用层（nonce + nc 计数器） | 传输层（TLS 序列号） |
| 凭证性质 | 每请求重算，近 PoP | bearer，长期复用同一串 |
| sessionId 泄露后 | 攻击者拿不到密码，难复用 | **直接可用，无第二道防线** |
| 拦 CSRF | 天然靠 nonce 隔离 | 必须靠 SameSite |

## 8. Cookie 安全属性详解

```
Set-Cookie: SESSIONID=abc123xyz; HttpOnly; Secure; SameSite=Lax; Path=/
```

### 8.1 HttpOnly —— 让 JS 读不到

> **先纠正一个常见混淆**：
> - **JS = JavaScript**（编程语言，页面上运行起来的脚本代码）
> - **JSON = JavaScript Object Notation**（数据格式，一串文本，不是程序）
>
> 两者完全不同。"JS 读不到"里的"读"，指页面上的脚本代码通过 `document.cookie` 读取。

**核心模型：浏览器里 cookie 有两个"出口"**

| 出口 | 谁用 | 可信吗 | HttpOnly 影响 |
|---|---|---|---|
| **网络出口** | 浏览器网络栈，拼 `Cookie:` 头 | 可信（浏览器自己） | 不影响，照带 |
| **脚本出口** | 页面 JS，走 `document.cookie` | 不可信（可能被注入） | **被拦** |

**为什么能做到**：`document.cookie` **不是透明窗**，它是浏览器实现的一个属性，读取时有段代码在过滤：

```
读取 document.cookie
  → 遍历可访问 cookie
  → 逐个检查：带 HttpOnly 吗？
       带 → 跳过
       没带 → 拼进结果串
  → 返回
```

所以不是"cookie 不见了"，是**被过滤掉了**。

**为什么这样设计**：页面 JS 不可信（可能是第三方脚本、统计代码、XSS 注入的代码）。浏览器无法分辨 → 就把"能冒充你身份"的凭证挪出脚本够得着的地方。网络栈是浏览器自己控制的，天然可信。

**动手验证**：
1. F12 → Application → Cookies：能看到 `SESSIONID`，Attributes 标注 **HttpOnly ✓**
2. Console 敲 `document.cookie`：**没有** `SESSIONID`（非 HttpOnly 的会正常出现）

**关键区分：读不到，但照样会发**
HttpOnly 只挡"脚本读"，不挡"浏览器发"。后续请求浏览器照带：
```
GET /orders
Cookie: SESSIONID=abc123xyz      # 浏览器自己做的，不经 JS
```

**为什么防 XSS**：XSS 链 = 注入 JS → 在受害者浏览器执行 → 读会话凭证 → 发给攻击者。
HttpOnly 卡在第三步：注入的 JS 能跑，但摸不到会话 cookie。

### 8.2 "万一浏览器不过滤呢"

**关键：cookie 存在谁的机器上？** 存在**受害者自己的浏览器**里，不在服务器、不在攻击者手里。
攻击者要偷，前提是**能在受害者浏览器里跑代码**（XSS）。他没法自己写浏览器去读——**要偷的 cookie 根本不在他机器上**。

分情况：

- **攻击者不遵守** → 无意义（cookie 不在他那）
- **受害者用了不遵守规范的浏览器** → 确实失效。但那种浏览器大概率对同源策略、CSP、混合内容拦截也都不上心——**你放弃的不是 HttpOnly 一层，是整栋房子的墙**
- **标准浏览器被绕过**：
  - 浏览器漏洞（历史上有绕过 HttpOnly 的 CVE）→ 所以要**纵深防御**
  - 恶意扩展（申请 `cookies` 权限可读 HttpOnly）→ 但需**用户亲手安装并批准**，性质是"你同意"不是"攻击"

**反例帮你想通信任根**：`curl`、Postman、Python 爬虫**全都能看到 cookie 明文**，HttpOnly 对它们毫无阻挡。
为什么不构成问题？——它们访问的是**自己客户端的自己的会话**，cookie 本就是它们自己的凭证，谈不上"偷"。

> **HttpOnly 不防"客户端读 cookie"（防不住也没必要），只切断一条特定攻击链：XSS 注入 → `document.cookie` 偷受害者会话。攻击者控制不了受害者用哪款浏览器，所以这条链只能靠浏览器老实实现规范来堵。**

**为什么能信浏览器**：不是"道德高尚"，而是**利益结构**——主流厂商有巨大商业动机正确实现安全规范。整个 Web 安全（HTTPS、同源策略、沙箱、HttpOnly）都建立在"用户使用主流浏览器"这个前提上。

### 8.3 Secure —— 防明文信道被截

> **纠正误解**：Secure **本身不加密任何东西**，也不是"加个说明让传输变加密"。真正加密的是 TLS（HTTPS）。**Secure 是"发送条件开关"——只准在加密信道上发，不加密就不发。**

**HTTPS 加密发生在离开浏览器之前**：

明文（浏览器内部）：
```
GET /orders HTTP/1.1
Host: example.com
Cookie: SESSIONID=abc123xyz
```
TLS 加密后上网线：
```
[随机字节....tls记录....随机字节]
```
路径上任何设备（路由器、运营商、公共 WiFi、中间节点）都只得乱码。密钥由 TLS 握手协商，只有两端掌握。

**Secure 的角色**：加密由协议层决定，但"cookie 该不该随某请求发送"由**浏览器**决定。Secure 让浏览器在"即将发出的请求协议"这关做检查：

```
浏览器准备发请求
  → 是 https 吗？
      是 → 把带 Secure 的 cookie 放进 Cookie: 头
      否 → 不带（cookie 留本地，这次不发）
```

**为什么需要它——两种降级场景**：
1. 用户手输 `http://`（默认 http）→ 明文请求，无 Secure 则 cookie 明文上路
2. https 页面嵌入 http 资源（如 `http://cdn.../track.gif`）→ 该请求是明文

**它防不了什么**：
- 防不了服务端泄露（服务器自己把 cookie 打进日志）——只管浏览器↔服务器这一段
- 防不了终端抓取（用户电脑被装恶意软件读本地存储）
- 防不了 HTTPS 被主动降级（需配合 **HSTS**：让浏览器**彻底拒绝**再以 http 访问该域名）
- **不加密内容**（加密是 TLS 的功劳）

> **一句话**：Secure 不是"加密开关"，是"发送条件开关"——借 HTTPS 已有的加密信道，规定"没加密时坚决不发"。

### 8.4 SameSite —— 防 CSRF

`SameSite=Lax / Strict / None`：控制跨站请求是否携带 cookie。
- 防 CSRF（第 7.3 ③）

## 10. 一页纸总结

1. **Digest** = 密码不上网，传指纹；因弱算法 + 强迫明文存储 + 不能注销而式微
2. **Session** = 服务器记账发座位号；能即时踢人，代价是有状态（多机需共享存储）
3. **Token vs Session** = 状态放哪；**JWT 是 Token 的一种格式**，特点是自包含 + 签名
4. **密码**：传输靠 HTTPS，存储必须加盐哈希（bcrypt/argon2）
5. **踢人**：refresh / 版本号 / 黑名单——"无状态"与"能踢人"天生互斥
6. **HTTP 无状态**，无原生 Session scheme；Session 认证架在 Cookie / Bearer 之上
7. **防重放**：Session 应用层不防，靠 TLS 序列号；sessionId 泄露则无第二道防线（bearer 凭证的宿命）
8. **HttpOnly** = 堵脚本出口（`document.cookie` 被过滤），网络出口照常
9. **Secure** = 发送条件开关，非加密开关（加密是 TLS）
10. **信任根**：主流水浏览器 + 纵深防御；curl/爬虫能看 cookie 明文但不构成"偷"（那是它自己的凭证）
